#### 새 원격 자료의 근거 연결 검사

평가 메타데이터 목록과 승인·MFA 참조 목록을 [로컬 검사기](../scripts/check_remote_evaluation_evidence.py)로 비교할 수 있다. 두 목록은 JSONL과 각각의 SHA-256으로 고정한다. 참조에는 사례 ID, 입력 SHA-256, 승인·MFA 기록별 SHA-256과 세션 그룹 지문, 기록이 최초로 이용 가능했던 시각과 관측 결과를 넣는다. 승인 거부와 MFA 비필수도 명시적으로 기록할 수 있고, 확인할 수 없는 결과는 미상으로 둔다.

```text
python -m scripts.check_remote_evaluation_evidence --catalog catalog.jsonl --catalog-sha256 CATALOG_PIN --evidence references.jsonl --evidence-sha256 REFERENCES_PIN
```

검사기는 입력 또는 세션 불일치, 사례 종료 후에 생긴 기록, 다른 세션에 재사용된 같은 기록과 미상을 구분한다. 참조 확인은 별도의 원본 무결성·출처·독립 라벨 검토나 추론·채점을 대신하지 않는다. 근거가 없는 사례의 정상·위협 라벨을 변경하지 않는다.

#### 외부 원격 접속 기록의 로컬 재생

Daniel Peng이 공개한 합성 인증 로그 180,000건에서 발행자가 지정한 보류 기간인 2026년 5월 16~30일의 성공한 `RemoteInteractive` 원격 로그온만 평가 대상으로 미리 고정했다. 기존 Sigma 원격 접속 경로에서 정답 없이 예측을 저장하고, 예측 파일의 해시 확인 후 발행자 라벨을 결합했다. #### 별도 로컬 인증원·보관 환경의 인수 시험

외부 인증원과 앱의 역할을 분리하기 위해 임시 RSA 키를 보유한 별도 루프백 OIDC 인증원을 사용했다. 앱은 HTTP로 공개 JWKS를 가져와 실제 서명을 검증했다. 정상 분석자 읽기, 뷰어의 회수 요청 거부, 대응 담당자의 세션 회수, 미사용 권한으로 회수 후 재접속 거부, 새 뷰어 토큰의 보호 작업 거부와 만료 토큰 거부를 테스트했다. 앱 세션 회수와 기업 IdP가 이미 발급한 토큰의 회수 전파는 별개 동작이다. 기업 IdP의 새 로그인·역할 매핑·강제 회수 정책 검증은 해당 조직의 환경이 있어야 진행할 수 있다.

별도 저장 HTTP 경로는 로컬 Docker 이미지 다운로드 권한 문제로 Moto 5.1.18의 별도 루프백 S3 서버를 사용했다. 격리 가상환경에 설치하고 검증 직후 서버를 종료했다. `AUDIT_LOCAL_S3_ENDPOINT=http://127.0.0.1:<port>`를 설정한 뒤 `tests/test_audit_witness_archive.py`를 실행하면 실제 HTTP 시험이 포함된다. 다른 테스트 클라이언트로 `COMPLIANCE` 보존 및 정확한 객체 버전을 확인했고, 보존 중인 버전 삭제는 `AccessDenied`로 거부됐다. 원본 경로 없이 내려받은 4,096개 서명과 암호화 백업을 복구 경로에서 검증하고 SQLite 파일을 열었다. 이 로컬 환경은 AWS 계정 간 IAM 강제, 실제 버킷 소유자 및 AWS 보존 정책의 운영 검증과 범위가 다르다.

#### 서울 리전 AWS 운영 인수 시험

`aitest-target`의 STS 계정이 `172585182454`와 일치한 뒤 서울 리전에서 조회했다. AWS S3에는 합성 감사 세대 한 개를 임시 버킷에 올렸다. 버전 ID·`COMPLIANCE`·보존 종료 시각·파일 및 서명 해시를 확인했다. 보존 중인 정확한 버전의 삭제를 요청했을 때 `AccessDenied`가 반환됐다. 원본 경로 밖에서 해당 버전을 내려받아 4,096개 서명과 별도 암호화 SQLite 백업을 확인하고 동일 감사 헤드의 SQLite를 열었다. 만료 뒤 시험 객체와 버킷을 삭제했다. 저장과 복원에 사용한 AWS 계정은 동일하며, 실제 별도 계정의 소유자·복구 권한 확인은 남아 있다. [S3 Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)

AWS Cognito의 임시 사용자가 발급받은 토큰으로 앱의 실제 JWKS 검증과 권한 경로를 실행했다. 분석자 토큰의 정책 요청은 200, 역할을 뷰어로 내린 뒤 새 토큰의 같은 권한 요청은 403이었다. `AdminUserGlobalSignOut` 뒤 Cognito API는 폐기된 액세스 토큰을 거부했지만, 앱의 서명·만료 확인만으로는 같은 사용자의 기존 ID 토큰이 200으로 통과했다. [Cognito 토큰 회수](https://docs.aws.amazon.com/cognito/latest/developerguide/token-revocation.html)

앱에 `OIDC_REVOKED_SUBJECTS_PATH`를 추가해 운영자 정책 파일의 발급자·테넌트·사용자 ID가 일치하는 요청을 즉시 차단한다. 분석 도중 차단이 추가되면 결과 게시 전에도 확인한다. 새 Cognito 시험에서는 전역 로그아웃 뒤 아직 만료되지 않은 같은 ID 토큰이 정책 등록 전 200, 등록 뒤 401이었다. 최초 시험의 ID 토큰도 실제 유효기간 경과 후 401로 거부됐다. 운영 정책 파일의 오류는 503으로 처리한다. 기업 IdP 자체의 회수 통지와 이 운영자 정책의 자동 연결은 이번 환경에서 검증하지 않았다. 앱 인증·회수 회귀는 106개 통과, 15개 제외였고 제로트러스트·OIDC·감사 정책 회귀는 289개 통과했다. 운영 자료 검증 준비 회귀는 111개 통과, 로컬 S3 서버 선택 실행 1개 제외였다. 회귀 묶음 간 중복이 있다.

임시 S3 버킷 1개와 Cognito 사용자 풀 2개를 삭제하고 각각 조회 실패를 확인했다. 외부 LLM 호출은 없었다. 직전 200·302 프로토콜 이상 미탐 106개에 대해, 개발·보정 구간에서 정상 흐름과 겹치는지 확인한 뒤 조건 세 가지를 고정했다. 각 조건은 같은 트레이스에서 HTTP 200과 302만 관측되고 관련 단계의 타임스탬프가 엄격히 증가할 때 적용한다.

- 연합 인증 컴포넌트 기록이 SP의 GET 302와 IdP의 GET 200 세 번으로 끝났다. 비교 구간에서 12개를 추가 탐지했다.
- 전체 트레이스에서 RP의 GET 302, OP의 GET 200, OP의 POST 200이 연속으로 관측되고 첫 요청부터 POST까지 5초를 초과했다. 비교 구간에서 16개를 추가 탐지했다. 요청 지연 자체는 위반의 확정 근거로 해석하지 않는다.

#### KREONET에서 정상과 같은 단계 순서를 갖는 흐름의 주체·클라이언트 연결

이전 판정에서 놓친 200·302 프로토콜 이상 75개 중 43개는 연합 인증 컴포넌트·HTTP 메서드·상태 코드의 순서가 정상과 같았다. 개발·보정 구간에서 같은 조건에 해당하는 미탐은 각각 210개·56개였다. 단계 간 간격만 사용하거나 전체 흐름의 IP가 바뀌었는지만 확인하면 정상적인 재시도와 컴포넌트 간 전달도 포함될 수 있어, 아래 두 조건을 두 구간에서 확인한 뒤 기존 비교 구간에 적용했다.

- `request`의 POST 200이 인접해 있고, 비어 있지 않은 사용자 ID는 같지만 로그에 기록된 IP와 User-Agent가 모두 바뀐다. 비교 구간의 대상 43개 중 5개를 추가 탐지했다.
- LDAP의 POST 200이 인접해 있고, 비어 있지 않은 IP와 User-Agent가 모두 같으며 두 요청 간격이 0초 초과 3초 이하다. 대상 중 3개를 추가 탐지했다. LDAP 사용자 ID가 비어 있는지 여부는 조건에 사용하지 않았다.

두 신호 모두 같은 트레이스에 200과 302만 관측된 경우에 적용한다. 타임스탬프는 상대 순서와 간격에, 사용자 ID·IP·User-Agent는 인접 관측의 동일 여부에만 사용했다. 원문 값은 예측 결과에 저장하지 않았다. 정답 라벨·분류·이벤트 이름·메시지·URL·페이로드는 신호에서 제외했으며, 테스트에서 해당 값을 바꿔도 예측이 같음을 확인했다. 로그에 기록된 사용자 ID와 클라이언트 값의 비교는 관측상 단서이며 실제 신원이나 기기 소유권을 확정하지 않는다.

#### Keycloak 승인·MFA·권한 회수 통합 시험

`scripts/run_keycloak_remote_acceptance.py`는 Keycloak 26.8.0의 임시 realm과 공개 키 조회를 루프백에 구성한다. 등록된 테스트 사용자의 비밀번호·TOTP로 로그인한 뒤 실제 HTTP 응답을 테스트 수집기의 MFA 관측으로 연결한다. 게이트웨이는 서명된 관측과 읽기 전용 자원 정책을 검사한다. Keycloak의 실제 역할 변경 및 로그아웃 결과를 확인하고 앱의 운영자 차단 목록을 갱신한다. 임시 계정, OTP, 토큰과 개인키는 결과 파일에 넣지 않는다. [Keycloak 컨테이너](https://www.keycloak.org/server/containers) · [Keycloak OTP 관리](https://www.keycloak.org/docs/26.8.0/server_admin/)

| 검증 항목 | 관측 결과 |
| --- | --- |
| 실제 TOTP | 올바른 OTP 200, 불일치·누락은 각각 400 `invalid_grant` |
| 승인 범위 | 서명된 MFA 성공과 읽기 권한으로 승인 및 실제 보호된 `READ` 통과. 같은 신호의 범위 밖 `REMOTE_ACCESS`는 `DENY`, 권한 미발급 |
| 실패한 MFA를 관측한 게이트웨이 | `STEP_UP`, 권한 미발급 |
| 역할 변경 | Keycloak에서 분석자 역할을 제거하고 조회자 역할을 추가한 뒤 새 토큰의 보호 요청은 403 |
| 로그아웃 및 이전 토큰 | Keycloak 로그아웃 204, 이후 갱신 400. 운영자 목록 갱신 후 이전 토큰은 401 |

기존 AWS Cognito 시험에서 확인한 새 토큰의 역할 제한과 운영자 목록 갱신 뒤 이전 토큰 거부를 로컬에서도 재현했다. Keycloak 시험에는 실제 TOTP와 게이트웨이의 승인·실패 분기를 추가했다. 차단 목록은 Keycloak 로그아웃 성공 확인 뒤 시험 실행기가 갱신했으며, 자동 Back-Channel Logout 수신 시험은 범위에 포함하지 않았다. 초기 시험은 realm 이름과 가져오기 파일명의 불일치로 기동에 실패했다. 파일 이름을 고쳐 다시 실행했고, 최종 결과는 `runtime/keycloak-remote-acceptance-20261121.json`에 보관했다. 테스트 컨테이너를 제거했다. 두 시험의 AWS 호출과 유료 모델 호출은 0회였다.
