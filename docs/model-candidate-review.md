# 작업별 인공지능 모델 검토 목록

검토일: 2026년 11월 1일 · 상태: 후보 조사와 비교 계획, 모델 설치·실제 API 시험 결과 없음

우리 프로젝트는 **LLM 기반 지능형 제로 트러스트 보안 오퍼레이션 및 자동화 프레임워크 구축**이다. LLM은 여러 세션 근거의 해석·설명·조사를 보조하고, 짧은 분류·검색·이상탐지는 해당 작업에 적합한 모델을 별도로 검토한다. 이 목록의 Jev·Laya를 포함한 모든 모델명은 **역할을 설명하는 예시와 비교 후보**이며 최종 채택 목록이 아니다. 후보를 모두 연결하는 것이 목표가 아니다.

## 영역별 우선 추천과 선정 근거

아래는 2026년 11월 1일 공식 자료와 현재 코드에 근거한 **우리 프로젝트의 우선 평가 추천**이다. 전체 시장의 성능 1위나 운영 채택 확정을 뜻하지 않는다. 공식 자료의 기능·가격, 저장소에서 확인한 구현, 적용에 대한 판단, 아직 검증하지 않은 조건을 구분한다. 모델 호출·설치·설정 변경은 수행하지 않았다.

### 1. 복잡한 분석의 첫 기준: GPT-6.1 Sol

**확인한 근거:** OpenAI Docs는 `gpt-6.1-sol`을 복잡한 전문 업무용으로 설명하고 구조화 출력과 여러 추론 강도를 지원한다고 명시한다. [공식 모델 명세](https://developers.openai.com/api/docs/models/gpt-6.1-sol)

**우리에게 맞는 이유:** 세션의 여러 이벤트를 모아 의심 변화, 정상일 수 있는 반대 근거, 부족한 신호, 근거 ID와 한국어 설명을 한 구조로 반환하는 품질 기준으로 추천한다. 저장소의 `app/analyzers/openai_analyzer.py`는 이미 Responses API의 구조화 응답을 사용하므로 연결 코드를 재사용할 출발점이 있다. 이는 GPT가 다른 공급자보다 정확하다는 증거가 아니라 개발 범위와 비교 조건을 관리하기 위한 선택이다.

**남은 검증:** 현재 기본 모델은 `app/config.py`와 `.env.example`의 `gpt-5.4-mini`이며 이번 수정으로 바꾸지 않았다. Sol은 현재 기본값인 `reasoning_effort=none`을 지원 목록에 포함하지 않으므로 그대로 모델명만 바꿔 연결 완료로 처리하지 않는다. 지원되는 추론 설정, 한국어 근거 충실도, 입력·출력 제한, 거절·빈 응답·시간 초과 처리를 검증해야 한다. 기존 분석기는 단건 이벤트용이며 세션 종합 분석은 별도 구현이다.

### 2. 비용을 줄일 생성형 경로: GPT-6 Luna

**확인한 근거:** 공식 명세는 `gpt-6-luna`를 집중된 대량 작업용으로 설명하고 구조화 출력과 `none`을 포함한 추론 설정을 지원한다. [공식 모델 명세](https://developers.openai.com/api/docs/models/gpt-6-luna)

**우리에게 맞는 이유:** 짧은 이벤트 유형 분류, 필드 추출과 한두 문장 요약을 생성형 모델로 처리하는 첫 저비용 비교군으로 추천한다. Jev와 달리 자유로운 설명도 함께 평가할 수 있고, 같은 공급자 연결 경로를 이용해 공급자 추가에 따른 구현 부담을 제한할 수 있다. 지원 기능의 일치는 현재 코드와의 연결 시험을 대체하지 않는다.

**가격 근거:** 확인 시점의 일반 Standard·짧은 입력 구간에서 100만 토큰당 Sol은 입력 $2·출력 $10, Luna는 입력 $0.10·출력 $0.50다. 같은 청구 토큰 수라면 두 단가 모두 20배 차이다. 이는 사건당 총비용이나 동일 정확도의 20배 개선을 뜻하지 않는다. 추론 토큰·캐시·긴 입력·재시도·추가 분석·처리 등급에 따른 차이를 포함해 다시 계산한다. [공식 API 가격](https://developers.openai.com/api/docs/pricing)

**남은 검증:** 한국어·영문 로그 혼합에서 미탐과 불필요한 조사 생략을 측정한다. 복잡하거나 근거가 부족한 사례를 이 경로만으로 종결하지 않는다. Gemini 3.8 Flash는 타 공급자 대안으로 유지하되 현재 조건에서 Luna보다 빠르거나 저렴하다고 단정하지 않는다. [Gemini 공식 명세](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash)

### 3. 판단 전용 모델의 첫 실험: Jev

**확인한 근거:** Jev는 상태와 정해진 질문을 받아 선택값·점수·참/거짓 판단 및 질문 유형별 확률·신뢰도를 반환한다. 공식 문서는 복잡한 질문을 작고 명확한 질문으로 나눠 코드에서 조합하도록 안내한다. [TypeSafe 공식 소개](https://docs.typesafe.ai/introduction)

**우리에게 맞는 이유:** 이벤트 유형, 조사 우선순위와 필요한 추가 분석을 정해진 선택지로 평가하는 인터페이스가 적합하다. 생성 문장을 해석하는 단계 대신 반환 형식·허용 선택지·범위를 검사하는 비교를 설계하기 쉽다. **판단 전용 실험에서 가장 먼저 평가**한다는 추천이며, 한국어 보안 분류의 정확도·최저 요금·최단 지연을 이미 입증했다는 뜻은 아니다.

**남은 검증:** 실제 계정 접근, 요금과 요청 제한, 데이터 보존·처리 조건, 한국어 품질, 질문·선택지 변화, 확률 보정과 네트워크 포함 지연은 아직 검증하지 않았다. 구조화된 결과에도 오판이 있을 수 있다. 정보 부족 선택지를 제공하고 실패 시 규칙 경로와 운영자 검토로 복구한다. GPT-6 Luna·단순 분류기와 비교해 추가 공급자를 운영할 이득이 없으면 채택하지 않는다.

### 4. 선택적 교차 검토: Claude Sonnet 5.5

**확인한 근거:** Anthropic은 `claude-sonnet-5-5`를 속도와 지능의 균형을 갖춘 모델로 안내한다. 확인 시점의 표준 단가는 입력 $2·출력 $10/100만 토큰이다. [공식 모델 명세](https://platform.claude.com/docs/en/models/sonnet-5-5/overview)

**우리에게 맞는 이유:** 같은 세션 근거에 대해 다른 공급자가 어떤 증거를 놓치고 어떤 근거 없는 결론을 추가하는지 비교할 두 번째 생성형 모델로 추천한다. 최초 비교에서는 Sol의 답을 보여주지 않고 각각 분석한다. 운영 적용이 검증되면 고위험·불명·근거 충돌 사례에만 선택적으로 요청하는 구성을 검토한다.

**남은 검증:** 공급자가 다르다는 사실은 오류가 통계적으로 독립이라는 뜻이 아니다. 두 모델의 동의로 접근을 허용하지 않는다. 교차 검토가 단일 모델 대비 실제로 줄인 오류·증가한 지연·비용·운영자 검토량을 평가한다. 구조화 응답 계약과 장애 처리를 위한 별도 연결도 필요하다.

### 5. 근거 검색: BGE-M3와 bge-reranker-v2-m3

**확인한 근거:** BGE-M3는 다국어 검색과 의미·단어 기반 검색 기능, 서로 다른 길이의 입력 처리를 지원한다. bge-reranker-v2-m3는 다국어 질문·문서 쌍의 관련성 점수를 계산한다. [BGE-M3 공식 카드](https://huggingface.co/BAAI/bge-m3), [재정렬 공식 카드](https://huggingface.co/BAAI/bge-reranker-v2-m3)

**우리에게 맞는 이유:** 한국어 플레이북과 영문 로그·사건 설명을 함께 검색할 후보로 BGE-M3를 먼저 추천한다. 이후 상위 검색 결과에만 재정렬을 적용해 분석에 필요한 근거를 추리는 구성을 시험한다. 다국어를 지원한다는 사실만으로 한국어 보안 검색 성능이 입증되지는 않는다. MiniLM과 키워드 검색을 더 가벼운 비교 기준으로 유지한다.

**남은 검증:** 검색은 M3~M5 필수 구현 이후 필요가 확인될 때 도입한다. 검색 전 테넌트·문서 접근권한·출처·버전을 제한한다. Recall@k·MRR/nDCG와 지연·메모리를 측정하고, 재정렬의 이득이 작으면 생략한다. 관련성 점수는 문서의 진위나 사용자의 신원 증명이 아니다.

### 6. 사용자 행동 이상탐지: Isolation Forest

**확인한 근거:** Isolation Forest는 특징값을 무작위로 분할했을 때 관측치가 얼마나 쉽게 분리되는지를 이용하는 이상탐지 방식이다. [scikit-learn 공식 문서](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.IsolationForest.html)

**우리에게 맞는 이유:** 시간대·접근 빈도·인증 실패율 등 수치형 행동의 첫 이상 점수 기준선으로 추천한다. 공격 라벨이 부족한 상황에서 비교를 시작할 수 있다는 설계 판단이다. 초기에 대규모 딥러닝 모델의 학습·운영 부담을 추가하기보다 이 기준선의 이득부터 확인한다.

**남은 검증:** 정상 업무 분포·시간대·직군을 반영한 충분한 관측 자료와 독립 평가가 먼저다. 무라벨 방식도 정답 평가 없이 정확도를 알 수 없으며, 새 직원·교대 근무·일시적 트래픽 증가가 오탐이 될 수 있다. 현재의 소수 시연 세션으로 학습·운영 채택하지 않는다. 점수는 조사 신호로만 사용한다.

### 7. 자체 실행과 과제 학습: Qwen3.5-4B, Laya multilingual

**생성형 자체 실행에는 Qwen3.5-4B를 먼저 추천한다.** 공식 카드는 4B 규모의 가중치, Apache 2.0과 자체 실행 방법을 제공한다. 입력·버전·실행 환경을 고정하고 외부 로그 전송 없이 비교할 출발점으로 선택한다. 한국어 보안 설명이 EXAONE나 API 모델보다 좋다는 주장은 하지 않는다. 하드웨어 적합성·양자화에 따른 품질·최대 입력·P95 지연을 측정한다. [Qwen 공식 카드](https://huggingface.co/Qwen/Qwen3.5-4B)

**로컬 판단 모델의 학습 연구에는 Laya multilingual을 추천한다.** Jev와 비슷한 선택형 작업을 자체 실행하고 학습·보정 전후를 비교할 수 있다. 다만 공식 카드의 기본 모델은 제시된 typed-decisions 무학습 평가에서 낮은 성능을 보였으며, 향상된 결과는 해당 과제로 학습한 체크포인트의 결과다. 그 결과를 우리 보안 데이터의 정확도로 사용하지 않는다. 현재 라벨과 보정 자료가 부족하므로 즉시 운영할 1순위로 추천하지 않는다. [Laya 공식 한계와 평가](https://huggingface.co/convaiinnovations/laya#honest-limits)

두 후보 모두 자체 실행의 전력·메모리·설치·업데이트·모니터링 비용을 포함한다. DeepSeek·GLM·EXAONE는 계속 대안으로 유지한다. 현재 범위에서 위 모델보다 낮은 성능이라고 결론 낸 것이 아니라, 공급자·운영 종류를 늘릴 필요가 생겼을 때 비교할 후보로 둔 것이다.

### 8. 접근 권한과 집행: 코드·정책 엔진 유지

이 프로젝트의 추천은 서명·권한·테넌트·신선도·만료·단일 사용·승인 검증을 코드로 재현하고 정책 엔진이 허용·재인증·회수를 결정하도록 유지하는 것이다. 이는 우리 프로젝트의 설계 선택이다. NIST의 정책 결정·집행 역할 구분을 참고하되 NIST가 특정 LLM 사용을 금지한다고 해석하지 않는다. [NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final)

LLM이 근거와 조사 권고를 생성해도 필수 검사·위험 규칙·승인을 우회하지 않는다. 생성형 모델의 구조화 출력이나 판단 모델의 높은 확률은 접근 권한의 증거가 아니다. AI 장애 시 기존 접근 집행의 안전 조건을 유지한다.

### 실제 평가 범위와 도입 순서

1. 기존 규칙과 현재 단건 분석을 기준으로 삼고, 생성형 품질 기준 Sol 1개와 타 공급자 비교 Sonnet 1개를 독립 평가한다. 세션 분석은 필요한 별도 입력·구현으로 명시한다.
2. 같은 짧은 분류에서 Jev·Laya·단순 분류기를 비교하고, 비용 절감 경로를 시험할 때 Luna를 추가한다. 라벨이나 실행 자원이 없는 항목은 미측정으로 남긴다. 후보 수를 채우려고 필수 세션·입력·집행 작업을 지연하지 않는다.
3. 초기에 AI는 관찰 모드로만 기록한다. 미탐·정상 업무 유지·근거 충실도 기준을 통과한 뒤 실제 네트워크·재시도·후속 호출을 포함한 사건당 총비용과 P95 지연으로 채택한다.
4. 검색·재정렬·이상탐지·자체 실행은 필요와 자료가 확보될 때 각각 평가한다. 최종 운영 모델은 추천 표 전체보다 적을 수 있다.

우선 추천은 새 실험 근거가 생기면 바꾼다. 기존의 11/8 평가 계약, 11/15 초기 실제 모델 시험, 11/29 독립 평가 일정과 M3~M5 우선순위는 유지한다. 이번 변경은 추천 근거 추가이며 유료 API 호출이나 운영 모델 전환을 수행한 것이 아니다.

## 선택 원칙과 실험 순서

1. **모델 없이 처리할 수 있는가:** 서명·권한·만료와 같은 정확한 검사는 코드로 수행한다. 분류도 규칙 기준선과 비교한다.
2. **출력이 무엇인가:** 선택·점수는 판단 모델/분류기, 설명·종합 해석은 생성형 LLM, 유사 자료는 임베딩·재정렬, 수치 행동 변화는 이상탐지를 검토한다.
3. **자료가 충분한가:** 학습·보정·튜닝은 개발 자료에만 수행하고 실제 평가셋을 따로 둔다. 작은 시연셋은 일반화 성능의 증거로 쓰지 않는다.
4. **전체 경로에서 이득이 있는가:** 단일 모델 추론보다 입력 준비·네트워크·재시도·두 번째 호출·사람 검토까지 포함한 미탐·정상 업무 유지·품질·비용·P95 지연을 비교한다.
5. **실패하면 어떻게 되는가:** 불명·분포 밖·오류·시간 초과에 규칙 경로와 검토 상태로 복구한다. 모델이 정상이라고 판단해도 필수 검증이나 위험 규칙을 생략하지 않는다.

실험 구성은 `규칙 전용`, `규칙+생성형 LLM`, `규칙+판단 모델+선택적 생성형 LLM`이다. 먼저 관찰 모드로 답을 기록하고 평가 기준을 만족한 기능만 점진적으로 채택한다. Jev·Laya의 정확도와 비용을 비교하는 실험, 생성형 모델의 한국어 설명을 비교하는 실험은 서로 다른 지표를 사용한다. 검색·이상탐지의 채택은 별도 과제로 승인된 범위 안에서 수행한다.

모든 후보를 동시에 시험하지 않는다. 11/8까지 생성형 기준 1개·타 공급자 비교 1개와 판단 후보 Jev·Laya·단순 기준선으로 첫 실험 범위를 좁힌다. 접근·라이선스·하드웨어 제약은 미측정 사유로 기록한다. 미측정 모델을 성능 순위에 넣지 않는다. 이후 교체·추가할 후보는 요구 미달의 원인과 해결 가설이 있을 때만 선정한다.

모델 API 비용은 사용자 허용 범위에서 실험별 요청·토큰·금액·시간 상한을 정해 관리한다. 현재 문서 수정에서는 호출·설치·계정 변경을 하지 않았으며 AWS 배포와 GitHub 업로드도 하지 않는다. 주간 일정과 평가 세부 기준은 [멘토링 피드백 우선 계획](mentoring-priority-roadmap.md)을 따른다.
