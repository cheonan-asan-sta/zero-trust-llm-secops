# 제로 트러스트 운영 구현 명세

작성 기준 2026년 10월 27일 · 애플리케이션 v0.17.0

이 프로젝트의 핵심은 접근 요청마다 신원·기기·자원·행위 신호를 평가하고, 세션 위험이 바뀌면 이전 허용을 회수하여 다음 접근을 거부하는 운영 흐름이다. v0.17은 이 흐름에 별도 수집기의 Ed25519 서명, 출처별 허용 범위, 현재 재인증 요청에 결합한 성공 신호와 수집기 키 폐기를 연결한다. 집행 대상은 계속 로컬 모의 자원이다.

## 적용 범위

- 새 `/zero-trust` 경로는 `local`·`test`에서만 제공한다. `production`에서는 404이며 SQLite 저장소도 초기화하지 않는다.
- 무서명 시연 경로와 서명 수집기 경로를 구분한다. 서명은 등록된 수집기가 보낸 신호의 출처·무결성을 확인한다. 내용이 실제 IdP 인증이나 EDR 기기 증명이라는 보장은 아직 없다.
- API 호출자의 인증·역할·테넌트와 관찰 대상 사용자는 구분한다. 허용은 호출한 모의 운영자에게도 묶인다.
- 집행 대상은 서버가 등록한 모의 문서와 모의 보관소뿐이다. 실제 AWS 계정·네트워크·업무 시스템을 변경하지 않는다.

## 판단과 집행 구조

```text
별도 로컬 수집기: 개인키로 접근 이벤트·테넌트·세션·버전·재인증 요청 서명
  → API: 고정 공개키 + 수집기 범위 + 신선도 + 서명 검사
  → 검증된 접근 이벤트 (무서명 시연은 별도 신뢰 모드)
  → 정책 엔진 PE
     서버 자원 정책 + 신호 유효기간 + 이전 세션 상태
     + 규칙 위험 점수 + Sigma 탐지 심각도
  → 정책 관리자 PA
     허용 또는 추가 인증 또는 보류 또는 거부
     허용 시 자원과 행위에 묶인 단일 사용 토큰 발급
  → 모의 정책 집행 지점 PEP
     현재 세션 버전과 상태 + 토큰 + 정책·출처 지문 + 키·신호·허용 유효기간 검사
  → HTTP 200과 모의 내용 또는 HTTP 403과 내용 없음
  → 판단과 집행 결과를 SQLite 트랜잭션 저널에 기록
```

기존 위험 분석·케이스 관리 API는 유지한다. 새 경로는 규칙 점수와 Sigma 탐지를 접근 정책 판단에 함께 사용한다. 기존 `/analysis`의 선택적 LLM 분석은 별도 기능이며, 새 PEP가 LLM 권고만으로 허용을 발급하지 않는다. 모든 엔드포인트는 요청 시 처리된다. 별도 수집기 도구도 명시적으로 실행하는 시연이며 백그라운드 구독·주기적 재평가는 아직 없다. 키·신호·토큰 만료와 출처 설정 변경은 다음 접근 시에도 검사한다.

## 제로 트러스트 원칙과 코드 매핑

| 원칙 | 구현 | 근거 |
|---|---|---|
| 네트워크 위치로 자동 신뢰하지 않음 | 사무실·VPN이라는 이유로 허용하지 않으며 IP 변경 시 재인증 요구 | `app/services/zero_trust.py` |
| 자원별 최소 권한 | 서버 정책의 역할·허용 행위·민감도 사용, 미등록 자원 거부 | `app/data/zero-trust-policies.json` |
| 세션 단위 승인 | 테넌트·운영자·사용자·기기·세션 식별자 결합 | `SessionDecision`, `evaluate` |
| 지속 재평가 | 새 이벤트마다 정책 판단·버전 갱신, 이전 토큰 즉시 무효화 | `evaluate`, `access` |
| 신호 품질 확인 | 인증 미확인·기기 상태 불명은 보류, 신호 만료·과도한 미래시각 차단 | `evaluate` |
| 신호 출처와 무결성 | 고정 Ed25519 공개키, 출처별 테넌트·사용자·기기·역할 범위, 신선도 검사 | `app/services/trusted_signals.py` |
| 현재 요청에 연결된 재인증 | 120초 무작위 챌린지에 결합한 새 서명 성공 신호 요구 | `evaluate_signed`, `_evaluate` |
| 허용 범위와 시간 제한 | 자원·행위별 1회 토큰, 기본 문서 60초·보관소 30초, 신호 만료시각을 넘지 않음 | 정책 번들, `access` |
| 위험 시 허용 회수 | 비활성·인증 실패·침해 기기·고위험·범위 위반 시 세션 회수 | `evaluate`, `revoke` |
| 검증 가능한 운영 이력 | 판단·근거·규칙 ID·정책 지문·입력 지문·접근 결과 기록 | SQLite `journal` |

MFA 미확인 상태는 `STEP_UP`이며 새 허용을 발급하지 않는다. 무서명 시연은 새 성공 값으로 복구할 수 있지만, 서명 세션은 현재 챌린지·버전·테넌트·세션을 포함한 새 서명이 필요하다. 중간 `HOLD`로 챌린지를 지울 수 없고 만료된 챌린지는 새 값으로 교체한다. `REVOKED` 세션은 정상처럼 보이는 새 입력만으로 되살릴 수 없다. 실제 MFA 수행과 복구 승인 연결은 후속 과제다.

## 서명 신호 계약과 키 수명주기

- 계약은 `zt-signal-1`, 알고리즘은 Ed25519로 고정한다. 검증된 모델을 JSON 직렬화한 뒤 서명 필드만 제외하고 키 정렬·UTF-8·공백 없는 바이트열을 서명한다. `canonical_signal`을 수집기와 검증기가 공유한다. 범용 JWS/JWT 계약은 아니다.
- 서명 범위는 이벤트 전체, `tenant_id`, `source_id`, `key_id`, `session_id`, `expected_version`, 발급·만료시각, `challenge_id`다. 입력 지문도 이 전체 계약을 사용한다.
- 신호 수명은 최대 120초, 수신 시 발급 이후 60초 이내, 미래 발급 거부, 이미 만료된 신호 거부다. 관찰 시각은 발급 시각을 넘을 수 없으며 자원 정책의 신호 나이도 별도로 적용한다. 수집기와 서버 시각 동기화가 필요하다.
- 출처는 특정 테넌트와 명시적 사용자·기기·역할 목록에 묶인다. 서명 유효성만으로 목록 밖의 권한을 부여하지 않는다. 자원별 역할·행위 정책도 계속 검사한다.
- API에는 공개키 등록 파일만 지정한다. 개인키는 별도 수집기에서만 보유한다. 원격 키 검색이나 외부 JWKS 호출은 없다.
- 키의 `enabled`, `not_before`, `not_after`를 검사하고 신호 만료가 키 만료를 넘지 못한다. 출처나 키 비활성화, 키 추가·회전, 범위 변경은 출처 지문을 바꾸므로 기존 허용은 다음 접근에서 거부된다. 새 서명 평가로 새 허용을 발급해야 한다.
- 등록 파일을 매 검증·서명 세션 접근 때 다시 읽는다. 오류·삭제·중복 ID·다른 키 유형이면 503으로 실패하며 허용하지 않는다. 미설정 상태는 서명 요청을 401로 거부한다. 등록 파일은 호스트 운영자의 신뢰 경계이며 변경 승인·원자적 교체·백업·개인키 보호는 실환경 연결 시 추가해야 한다.
- 서명 세션은 `verified_source`로 기록되며 같은 세션의 무서명 전환이나 다른 출처 전환은 409다. 무서명 세션도 중간에 서명 세션으로 바꿀 수 없다. 키 회전은 같은 출처의 새 평가로 처리한다.
- 챌린지는 120초 유효한 무작위 값이며 서명 성공 신호 발급시각이 직전 판단시각보다 뒤여야 한다. 성공하더라도 현재 위험·자원 정책을 충족해야 허용한다. 허용되면 챌린지를 비우므로 다른 이벤트로 재사용할 수 없다.

서명은 수집기가 보낸 주장의 출처를 검증한다. 수집기 개인키 침해, 허용된 수집기의 거짓 주장, 실제 사용자의 MFA 미수행까지 방어했다고 해석하면 안 된다. 실제 IdP/EDR 연결과 각 신호의 권위·정책을 분리하는 설계가 필요하다.

## 실패와 일관성 처리

- 동일 이벤트 ID와 동일 입력은 중복으로 처리하고 버전·허용을 추가하지 않는다. 원문 토큰도 재노출하지 않는다.
- 같은 ID의 다른 입력, 다른 세션에서 재사용한 ID, 이전 시각의 이벤트, 사용자·기기 결합 변경, 예상 버전 충돌은 409다. 지연 이벤트 자동 재정렬은 하지 않는다.
- SQLite `BEGIN IMMEDIATE`로 판단·회수·허용 소비를 직렬화한다. 같은 허용의 동시 접근은 1건만 성공한다.
- 저널은 단일 상태 원본이다. 읽기·쓰기·접근마다 순번과 SHA-256 체인을 확인한다. 손상·저장 오류는 503이며 모의 내용은 반환하지 않는다.
- 원문 토큰 대신 해시만 보관한다. 응답은 기존 보안 미들웨어의 `Cache-Control: no-store`를 적용한다.
- 세션당 판단 200건, 전체 저널 10,000건의 로컬 실험 상한을 둔다. 최종 세션 버전에서는 새 허용을 발급하지 않는다. 상한 도달 후 운영 아카이브·갱신은 별도 설계 대상이다.
- 해시 체인은 외부에 고정한 서명 앵커가 아니다. 전체 DB 교체·접미부 삭제·호스트 관리자 변조를 모두 탐지한다고 주장하지 않는다.

## API

| 경로 | 권한 | 동작 |
|---|---|---|
| `GET /zero-trust/policies` | viewer | 서버 자원 정책 조회 |
| `POST /zero-trust/sessions/evaluate` | analyst | 이벤트별 세션 판단과 허용 발급 |
| `POST /zero-trust/signals/evaluate` | analyst | 서명·출처·범위·신선도 검증 후 세션 판단 |
| `GET /zero-trust/signals/status` | viewer | 공개키 등록 파일 상태·설정 여부·등록 출처 수 |
| `GET /zero-trust/sessions` | viewer | 현재 테넌트의 최근 세션 최대 100개 |
| `GET /zero-trust/sessions/{session_id}` | viewer | 세션 판단 이력 |
| `POST /zero-trust/sessions/{session_id}/revoke` | responder | 버전 확인 후 수동 허용 회수 |
| `POST /zero-trust/protected-access` | analyst | 토큰을 검사하는 모의 PEP |

조회는 테넌트 범위다. 평가·허용 사용은 해당 모의 운영자에 묶이고, responder는 같은 테넌트의 세션을 회수할 수 있다. 로컬 기본 인증 비활성 모드는 모의 관리자다.

## 비용 없는 서명 수집기 종단 시험

권장 경로는 `pwsh -File scripts/test-docker.ps1`이다. 테스트 이미지에서 임시 수집기를 초기화하고 API에는 공개키 파일만 읽기 전용으로 마운트한다. 별도 수집기 컨테이너만 개인키를 가지며 API 컨테이너의 루프백으로 요청한다. 종료 시 시험 컨테이너와 임시 키 파일을 제거한다. AWS 배포와 유료 LLM 호출은 하지 않으며 `ANALYZER_MODE=rule`을 사용한다.

직접 실행할 경우 다음 순서를 따른다. 기존 파일을 덮어쓰지 않으므로 새 디렉터리를 사용한다.

```powershell
python -m scripts.local_signal_collector init --directory runtime/local-collector --tenant local
$env:ANALYZER_MODE = "rule"
$env:TRUSTED_SIGNAL_SOURCES_PATH = "runtime/local-collector/sources.json"
python -m uvicorn app.main:app --host 127.0.0.1 --port 18080
```

같은 가상환경의 다른 터미널에서 실행한다.

```powershell
python -m scripts.local_signal_collector demo --directory runtime/local-collector --tenant local --base-url http://127.0.0.1:18080
```

이 도구는 HTTP 루프백만 허용하고 리다이렉트를 거부한다. 개인키·서명 원문·허용 토큰을 출력하지 않는다. `runtime/local-collector/`는 Git과 Docker 빌드에서 제외된다. 직접 실행 시 서버 종료와 생성한 키 폐기는 사용자가 관리한다. 기본 인증 비활성인 로컬 시연용 도구이며 실제 인증 서비스나 상시 수집기는 아니다.

종단 순서는 서명 정상 허용과 접근 200 → MFA 미확인 → 요청 결합 없는 성공 신호의 `STEP_UP` 유지 → 챌린지에 결합한 새 성공 신호의 허용 → 기기 침해 회수 → 미사용 허용의 403이다. 대시보드의 **서명 세션 조회**는 최근 100개 세션 중 서명 세션의 출처·키·판단·재인증 대기·근거를 조회한다. 브라우저에 개인키를 넣거나 브라우저가 성공 증명을 자체 발급하지 않는다.

## 시연과 검증

1. 대시보드의 정상 세션 시작으로 `ALLOW`와 1회 허용을 확인한다.
2. 모의 문서 접근은 200이다. 같은 허용을 다시 사용하면 403이다.
3. MFA 미확인 재평가로 `STEP_UP`을 확인한다. 다음 문서 접근은 403이다.
4. MFA 성공 재평가는 새 버전과 새 토큰을 만든다.
5. 기기 침해 재평가는 `DENY`·`REVOKED`다. 직전의 사용하지 않은 토큰도 403이다.
6. 이후 MFA 성공 신호를 보내도 회수된 세션은 계속 거부된다.

`tests/test_zero_trust_operations.py`는 기존 운영 흐름 28건, `tests/test_trusted_signals.py`는 서명·위조·출처 범위·신선도·모드 전환·챌린지 우회·동시 갱신·키 폐기·회전·재시작·등록 오류·API 역할과 프로덕션 비활성화·수집기 로컬 제한 27건을 확인한다. `scripts/test-docker.ps1`은 별도 수집기를 사용해 요청 결합 없는 MFA 거부, 결합한 신호의 복구와 회수 후 접근 거부까지 검사한다. 이는 모의 운영 흐름의 기능 검증이며 실사용자 탐지 성능, 운영 처리량 또는 NIST 인증을 의미하지 않는다.

2026년 10월 27일 검증 결과: 로컬과 Docker 내부 전체 177건 통과, 제로 트러스트 운영·서명 신호 전용 55건 포함, Ruff 및 JavaScript 문법 검사 통과. Docker API 종단 시험에서 `signed_source_verified=true`, `unbound_mfa_rejected=true`, `bound_mfa_recovered=true`, `signed_revoked_grant_denied=true`를 확인했다. 화면 클릭 검증은 수행하지 않았으며 브라우저 표시 상태까지 확인한 것으로 간주하지 않는다.

## 운영 확장 순서

실제 IdP의 세션·재인증 증명과 EDR 기기 증명 → 신호별 권위와 수집기 키 관리·승인·시각 동기화 → 지연 신호 조정과 상시 수집 → 외부 정책 집행 지점 연결 → 정책 변경 서명·감사 앵커 → 부하·장애·복구 시험 순으로 확장한다. 현재 신호 내용은 모의 입력이므로 프로덕션에서 새 경로를 활성화하지 않는다. GuardDuty 커넥터와 실제 자원 차단은 이번 구현에 포함하지 않았다.

설계 참고: [NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final). 원칙과 구성요소를 구현에 매핑한 것이며 NIST 적합성 인증 선언은 아니다.

서명 구현 참고: [cryptography Ed25519 API](https://cryptography.io/en/latest/hazmat/primitives/asymmetric/ed25519/). API가 제공하는 키 생성·서명·검증을 사용하며 암호 알고리즘을 자체 구현하지 않는다.
