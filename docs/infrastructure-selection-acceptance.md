## 초기 실행과 보완

첫 실제 Docker 실행은 release검사7개·첫 반복 부하9개·gateway복구1개를 통과한 뒤,
두 번째 반복의 정상 요청에서 기대16건과 자원 전달 수가 달라 중단했다. 정확한 실패 wave의
응답/전달 수는 당시 저장되지 않아 원인을 단정하지 않는다. Docker 이벤트에 OOM/재시작은
없었고 자원 수집770행/오류0·소유 자원0이었다. 이 소스의 Linux2555개는 별도로 통과했다.

보완 소스는 실패 wave도 판정 전에 상태·본문 지문·TLS·시간·기대/실제 전달 수를 저장한다.
또 core 직접 health 대신 기존 collector신원으로 실제 gateway를 경유하는 잘못된 inbox요청의422를
확인한다. 서명 이벤트 접수·권한 소비가 없는 준비 확인이며 기존 역할/통신 허용 범위를 늘리지 않는다.
처음 실패의 원인이 이 준비 확인이었다고 단정하지 않는다. 정상16건·shared1건·재사용/누락0건의
조건과 운영TTL·timeout·인가·탐지 기준은 유지한다. 실패 기록은 성공으로 바꾸지 않는다.

두 번째 실행은19개 검사 뒤 동시성8·grant누락 wave에서403이15개,500이1개였다.
16요청 모두 실제 문서 전달0이었으나 엄격한403 기준을 통과시키지 않았다. core직접 확인을
실제 gateway경유422로 바꾼 것만으로 이 현상이 해결됐다고 표시하지 않는다. 실패 응답·기대/실제
전달 수·TLS/시간을 보존했고 소유 자원0으로 정리했다. 영향을 받는 실제 검증을 먼저 해결하기 위해
이후 독립 Linux 실행은 자신의 정확한 label/이름을 확인해 중단했고 통과 수로 집계하지 않는다.

별도 loopback TCP재현에서는 accept를 잠시 진행하지 않는 실제 두 서버의 대기열5에서8연결 중6개만
성공했다. 서버 초기 인증서 설정만 stub한 TCP 대기열 시험이며 TLS 인증/인가 시험은 아니다.
이를 회귀2개로 고정하고 Gateway의 유한 대기열을32로 명시해 NativeServer에도 상속했다.
기존 PID/CPU/메모리 제한·mTLS 인증·역할·pin·운영TTL/timeout·정상16/shared1/거부0 기준은 유지한다.
수정 후 관련190개와 실제 Docker 검증을 연결한다. 개별500의 패킷 원인을 모두 추적한 증거는 아니며,
재현된 작은 대기열의 연결 누락을 보완한 것이다. 임의의 DoS·과부하를 모두 해결했다는 뜻은 아니다.

[Python3.12 socketserver 공식 설명](https://docs.python.org/3.12/library/socketserver.html#socketserver.TCPServer.request_queue_size)은
대기열이 가득 차면 추가 연결이 거부될 수 있고 하위 클래스에서 크기를 지정할 수 있음을 설명한다.
32는 이번8동시요청 로컬 범위의 명시적 설정이며 운영 용량/SLA 권고 수치가 아니다.
대기열에 들어간 연결을 인가된 요청으로 취급하지 않는다. 기존 TLS chain/hostname/pin·요청별 서비스 역할과
단일 사용 허용 검사를 그대로 통과해야 하며, 새 역할·새 통신 경로·권한 자동 복구를 추가하지 않았다.
