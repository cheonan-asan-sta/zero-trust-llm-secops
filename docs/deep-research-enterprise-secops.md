# Zero Trust LLM SecOps 고도화 딥 리서치

- 조사일: 2026-09-16
- 대상 버전: `0.7.0` (`aitest` 브랜치)
- 조사 범위: 제로 트러스트, 보안 로그 표준화, 탐지·상관분석, LLM 기반 SOC, 대응 자동화, 정책 검증, 평가 데이터셋

## 1. 결론 요약

현재 프로젝트의 `규칙 우선 → 필요할 때 LLM 보조 → 결정론적 안전장치 → 사람 승인` 구조는 연구 결과와 잘 맞는다. 다음 고도화의 중심은 더 큰 LLM을 붙이는 것이 아니라 아래 네 가지여야 한다.

1. 입력 이벤트를 OCSF 기반 공통 스키마로 정규화하고 원본 증거와 변환 이력을 보존한다.
2. 단일 이벤트 판정에서 시간창·사용자·기기·세션을 연결하는 사건 상관분석으로 확장한다.
3. 탐지와 대응 정책을 코드에서 분리해 Sigma와 Cedar 또는 OPA 정책으로 버전 관리한다.
4. 합성 8건 중심 평가를 실제 공개 로그, 공격 재현 로그, 프롬프트 공격 세트로 확대한다.

권장 목표 구조는 다음과 같다.

```text
로그 수집기
  → OCSF 정규화·검증·중복 제거
  → 원본/정규화 이벤트의 변경 불가 저장
  → Sigma·규칙 기반 1차 탐지
  → 시간창·엔터티 기반 상관분석
  → 제한된 범위의 LLM 설명·요약·가설 생성
  → 결정론적 정책 검증기
  → 사람 승인
  → CACAO 형식의 대응 미리보기 또는 승인된 실행
```

최신 연구는 LLM을 단독 탐지기나 자율 대응기로 사용하는 것을 지지하지 않는다. 반면 로그 요약, 증거 정리, 제한된 분류, 대응 계획 초안처럼 경계가 명확한 보조 업무에서는 생산성 향상 가능성이 확인된다.

## 2. 조사 방법과 근거 등급

마케팅 요약보다 원 논문, 공식 표준, 운영 조직이 직접 공개한 기술 자료를 우선했다.

| 등급 | 의미 | 사용 원칙 |
|---|---|---|
| A | 동료심사 논문, 정부·표준기구 최종 문서, 상세한 운영 논문 | 설계 원칙과 합격 기준의 핵심 근거 |
| B | 재현 가능한 프리프린트, 공개 코드·데이터가 있는 연구, 공급자 수행 RCT | 실험 후보와 방향성 근거, 재검증 필요 |
| C | 기업 기술 블로그·고객 사례 | 구현 아이디어 참고, 독립 검증 전 성능 근거로 사용하지 않음 |

2025~2026년 프리프린트는 최신성이 높지만 동료심사를 거치지 않았을 수 있으므로 별도로 표시했다.

## 3. 실제 적용 사례

### 3.1 Google BeyondCorp: 네트워크 위치 대신 사용자·기기 맥락

Google은 사내망 자체를 신뢰 경계로 보지 않고 사용자, 기기 상태, 애플리케이션 정책을 기준으로 접근을 결정하는 BeyondCorp를 설계했다. 이후 공개한 배포·마이그레이션 자료는 대규모 전환을 한 번에 하지 않고 애플리케이션과 사용자 집단을 단계적으로 옮겼다는 점을 강조한다.

- 근거: [BeyondCorp: A New Approach to Enterprise Security](https://research.google/pubs/beyondcorp-a-new-approach-to-enterprise-security/), [Design to Deployment at Google](https://research.google/pubs/beyondcorp-design-to-deployment-at-google/), [Migrating to BeyondCorp](https://research.google/pubs/pub46134)
- 등급: A/C. 설계·운영자가 직접 공개한 운영 자료다.
- 프로젝트 적용: 현재 `user/device/network/resource` 맥락을 인증 시점뿐 아니라 매 분석 요청의 정책 입력으로 유지한다. 이후에는 기기 준수 상태, 토큰 위험도, 최근 인증 강도, 자원 민감도를 정책 엔진에서 함께 평가해야 한다.
- 주의점: 특정 공급자의 제품을 복제하기보다 단계적 도입과 지속 평가라는 운영 패턴을 가져오는 것이 중요하다.

### 3.2 Google Zanzibar: 애플리케이션 밖에서 일관된 권한 판정

Zanzibar는 Google의 여러 서비스가 공통 데이터 모델로 권한을 확인하도록 만든 전역 권한 시스템이다. 논문은 수조 개 ACL, 초당 수백만 건의 권한 확인, 3년간 99.999% 이상의 가용성과 10ms 미만 P95 지연을 보고했다.

- 근거: [Zanzibar: Google’s Consistent, Global Authorization System](https://www.usenix.org/system/files/atc19-pang.pdf)
- 등급: A. USENIX ATC 운영 논문이다.
- 프로젝트 적용: 현재 엔드포인트 안에 섞여 있는 역할·테넌트·검토 권한을 정책 결정 지점과 집행 지점으로 분리한다. 지금 규모에서는 Zanzibar급 시스템이 필요하지 않지만, `principal/action/resource/context` 계약을 먼저 고정하면 Cedar·OPA·외부 권한 서비스로 이전하기 쉽다.

### 3.3 Airbnb StreamAlert: 대량 로그도 규칙과 스키마가 중심

Airbnb가 공개한 StreamAlert는 서버리스 실시간 로그 분석 구조로, Python 규칙, 다양한 로그 스키마, 과거 검색, 잡음이 낮은 규칙의 승격을 제공하며 하루 테라바이트 규모의 로그 스캔 사례를 설명한다.

- 근거: [Airbnb StreamAlert](https://airbnb.tech/opensource/streamalert/)
- 등급: C. 운영 조직의 기술 자료이며 독립 벤치마크는 아니다.
- 프로젝트 적용: LLM보다 먼저 `정규화 → 규칙 실행 → 경보 병합 → 과거 재생` 경로를 만든다. 규칙마다 상태, 버전, 오탐 메모, 적용 로그원을 보관한다.

### 3.4 Microsoft Security Copilot RCT: 보조 분석은 유용하지만 범위가 좁다

Microsoft가 147명의 보안 전문가를 대상으로 수행한 무작위 대조시험에서는 Copilot 사용 그룹이 전체 업무를 22% 더 빠르게, 7% 더 정확하게 수행했다고 보고했다. 다만 실험은 랜섬웨어와 BEC라는 두 개의 준비된 시나리오, 자사 제품 환경에서 수행됐다.

- 근거: [Microsoft Copilot for Security RCT 요약](https://www.microsoft.com/content/dam/microsoft/final/en-us/microsoft-brand/documents/EconStudy-Speed-accuracy-and-sentiment-Infographic-Final.pdf)
- 등급: B. 무작위 대조시험이지만 공급자가 직접 수행했고 과제 범위가 제한적이다.
- 프로젝트 적용: KPI를 “LLM이 맞혔는가”만으로 잡지 말고, 분석 완료 시간, 증거 누락률, 보고서 사실 수, 분석가 수정량을 함께 측정한다.

### 3.5 OCSF 기반 AI SOC 사례: 공통 언어가 AI보다 먼저

AWS가 공개한 eightcap 사례는 AWS·SaaS·거래 시스템의 서로 다른 텔레메트리를 OCSF로 통합한 뒤 AI 기반 분석을 적용했다고 설명한다.

- 근거: [AWS: Powering AI-Driven Security with OCSF](https://aws.amazon.com/blogs/opensource/powering-ai-driven-security-with-the-open-cybersecurity-schema-framework/)
- 등급: C. 공급자 고객 사례이므로 구조적 참고 자료로만 사용한다.
- 프로젝트 적용: 다양한 로그를 프롬프트에 바로 넣지 말고 먼저 공통 이벤트 스키마로 변환한다. 변환 실패·누락 필드·원본 위치를 품질 지표로 관리한다.

## 4. 핵심 논문 분석

### 4.1 로그 이상탐지의 발전과 적용 한계

| 연구 | 핵심 결과 | 이 프로젝트에 주는 의미 |
|---|---|---|
| [DeepLog, CCS 2017](https://www2.cs.utah.edu/~lifeifei/papers/deeplog.pdf) | 정상 로그 순서를 LSTM으로 학습하고 새로운 패턴에 온라인 적응 | 단일 이벤트 점수보다 순서와 세션 문맥이 중요하다. 비교 기준선으로 적합하다. |
| [LogBERT, IJCNN 2021](https://par.nsf.gov/servlets/purl/10317798) | 정상 로그의 마스킹 예측과 표현 공간 학습을 결합한 자기지도 이상탐지 | 라벨이 적은 환경에서도 정상 패턴 학습이 가능하지만 로그 파싱 품질에 영향을 받는다. |
| [Robust and Transferable Anomaly Detection, 2021](https://arxiv.org/abs/2102.11570) | 사전학습 언어모델 표현이 로그 형식 변화와 콜드스타트에 더 견고할 가능성 | 공급자별 표현 변화에 대한 별도 회귀시험이 필요하다. |
| [LogGPT, 2023](https://arxiv.org/abs/2309.14482) | 다음 로그 예측 뒤 이상탐지 목적의 강화학습을 추가 | 언어모델 손실이 곧 탐지 성능은 아니므로 탐지 목적에 맞는 평가·보정이 필요하다. |
| [AIRTAG, USENIX Security 2023](https://www.usenix.org/conference/usenixsecurity23/presentation/ding-hailun-airtag) | 19개 단·다중 호스트 공격에서 로그 텍스트를 직접 분석해 기존 ATLAS보다 2.5배 빠르고 평균 거짓양성 9.0% 감소, 참양성 16.5% 증가 | 이벤트별 판정 이후의 우선 연구 목표는 공격 이야기와 관련 엔터티 복원이다. |

이 계열 논문은 현재 규칙 분석기를 폐기할 근거가 아니다. 정상 패턴 기반 이상탐지는 알려지지 않은 행동을 찾는 보조 신호로 사용하고, 기존 정책 위반·명시적 공격 패턴은 결정론적 규칙이 담당하는 혼합 구조가 적절하다.

### 4.2 LLM 기반 SOC의 가능성과 강한 반례

| 연구 | 관찰 | 판단 |
|---|---|---|
| [OpenSOC-AI, 2026 프리프린트](https://arxiv.org/abs/2604.26217) | 1.1B 모델을 450개 예제로 LoRA 학습해 위협 분류 68%, 심각도 58%, F1 0.68을 보고 | 저비용 로컬 모델 가능성은 있지만 기업 자동판정 기준으로는 부족하다. 요약·후보 생성용 실험에 적합하다. |
| [AuditBench, 2026 프리프린트](https://arxiv.org/abs/2606.10281) | Windows·Linux 50여 개 조사 시나리오로 다섯 개 프런티어 모델의 로그 조사 능력과 오류 유형을 비교 | 모델 비교는 지식문답이 아니라 실제 로그 증거 찾기·지속성 규명·설명 근거성으로 해야 한다. |
| [Cyber Defense Benchmark, 2026 프리프린트](https://arxiv.org/abs/2604.19533) | 75,000~135,000건 로그, 106개 공격 절차 환경에서 최고 모델도 악성 이벤트를 평균 3.8%만 정확히 표시했고 완전 성공은 없었다 | 개방형 위협 헌팅을 LLM에 단독 위임하면 안 된다. 검색 공간 축소와 규칙·쿼리 도구가 필수다. |
| [ATT&CK 다중 라벨 분류 연구, 2026 프리프린트](https://arxiv.org/abs/2606.18166) | 복잡한 CTI 보고서에서 최고 오픈 모델의 micro-F1이 0.22였고 프롬프트·온도 변경은 유의미한 개선이 없었다 | 현재 정적 ATT&CK 라벨을 LLM 자동 매핑으로 대체하지 말고 후보 제안 후 사람 검증을 유지한다. |
| [Large Language Models for SOCs Survey, 2025 프리프린트](https://arxiv.org/abs/2509.10858) | 분류·요약·트리아지·위협 인텔리전스 활용을 정리하면서 환각, 개인정보, 지연, 평가 부족을 공통 문제로 제시 | 각 LLM 기능을 독립적으로 켜고 끌 수 있고 규칙 기반 폴백이 있어야 한다. |

가장 중요한 연구 결론은 “더 큰 모델”보다 “더 작은 과제”가 먼저라는 점이다. LLM 입력은 한 사건의 제한된 증거 묶음으로 축소하고, 출력은 근거 ID가 있는 구조화된 가설·요약·다음 조사 질문으로 제한해야 한다.

### 4.3 대응 계획은 LLM 출력 뒤에서 다시 검증해야 한다

[SOCpilot](https://arxiv.org/abs/2605.05501)은 금융권 운영 SOC의 익명화된 실제 사건 200건을 바탕으로 LLM 대응 계획을 검증했다. 결정론적 검증기는 승인 절차를 위반한 조치 466개를 제거하면서 기준 업무 재현율을 낮추지 않았다고 보고했다. 아직 프리프린트지만 현재 프로젝트의 정책 엔진과 사람 승인 설계를 직접 지지한다.

적용 원칙은 다음과 같다.

- LLM은 실행 명령이 아니라 `제안된 조치`만 만든다.
- 정책 검증기가 허용된 조치 목록, 필수 선행 단계, 순서, 대상 범위, 승인자를 확인한다.
- 검증 실패는 조용히 수정하지 않고 어떤 정책 때문에 차단됐는지 기록한다.
- 계정 비활성화, 세션 종료, 네트워크 격리, 권한 변경은 항상 별도 승인 토큰을 요구한다.
- 동일 사건과 동일 조치에 대해 중복 실행을 막는 idempotency key를 사용한다.

대응 플레이북 표현은 [OASIS CACAO Security Playbooks 2.0](https://www.oasis-open.org/standard/cacao-security-playbooks-v2-0/)을 우선 검토할 가치가 있다. CACAO는 조사·완화·복구 단계를 기계가 처리할 수 있는 구조와 서명 가능한 플레이북으로 표현한다.

### 4.4 프롬프트 인젝션은 모델 지시만으로 해결되지 않는다

[CyberSecEval 2](https://arxiv.org/abs/2404.13161)은 평가한 모델에서 프롬프트 인젝션 성공률 26~41%를 관찰했다. [Instruction Hierarchy](https://openai.com/index/the-instruction-hierarchy/)는 신뢰 수준이 다른 지시를 구분하도록 학습하면 방어력이 개선됨을 보였지만 완전한 시스템 보증은 아니다. [CaMeL](https://arxiv.org/abs/2503.18813)은 신뢰된 제어 흐름과 외부 비신뢰 데이터를 분리하고 capability로 데이터 흐름을 제한해 AgentDojo 과제의 67%를 증명 가능한 보안 조건 아래 해결했다.

프로젝트에는 다음 통제가 필요하다.

- `event_text`, 로그 메시지, CTI 문서는 모두 명령이 아닌 비신뢰 데이터로 태깅한다.
- 비신뢰 문자열에서 도구 이름·실행 인자를 직접 만들지 않는다.
- LLM은 원본 자격증명, 다른 테넌트 데이터, 비공개 시스템 프롬프트에 접근하지 않는다.
- 도구 호출이 추가되더라도 정책 엔진이 대상·인자·데이터 유출 경로를 별도로 승인한다.
- 정상 업무를 과도하게 거부하는 비율도 함께 측정한다.

### 4.5 권한 정책은 애플리케이션 코드에서 분리할 수 있다

[Cedar 논문](https://arxiv.org/abs/2403.04651)은 RBAC·ABAC·관계 기반 패턴을 읽을 수 있는 정책으로 표현하고 분석 가능하도록 설계된 권한 언어를 제안한다. Cedar는 로컬 오픈소스로 실행할 수 있어 AWS 비용 없이 실험할 수 있다. 대안인 [Open Policy Agent](https://www.openpolicyagent.org/)도 구조화 데이터에 대한 정책 평가와 중앙 정책 관리를 제공한다.

현재 프로젝트에는 다음 계약이 적합하다.

```text
principal = 사용자/서비스 + 역할 + tenant + 신뢰 속성
action    = view, analyze, review, approve, execute
resource  = event, incident, playbook, response_action
context   = 위험도, 기기 상태, 인증 강도, 시간, 요청 ID, 승인 상태
```

첫 단계에서는 Cedar와 OPA를 동시에 도입하지 않고, 로컬 실행·Python 통합·정책 분석 편의성을 비교하는 작은 실험 뒤 하나를 선택한다.

## 5. 도입할 표준과 역할

ATT&CK는 지속적으로 갱신되므로 최신 데이터를 무조건 따라가기보다 버전을 고정하고 변경 영향 테스트 뒤 승격해야 한다. 현재 공식 STIX 저장소도 릴리스별 컬렉션을 제공한다.

## 6. 현재 프로젝트와 연구 기준의 차이

### 이미 잘 되어 있는 부분

- 규칙·LLM·하이브리드 분석기를 분리하고 LLM 실패 시 규칙으로 폴백한다.
- 위험 점수와 행동의 불일치를 결정론적 안전 로직이 다시 확인한다.
- 실제 조치를 수행하지 않고 미리보기와 사람 검토 상태를 유지한다.
- 이벤트 구조, 정책 예외, 테넌트 격리, 역할, 요청 추적과 감사 로그가 있다.
- 합성 시나리오에 ATT&CK 기법, 정상 예외, 기대 위험도와 조치가 연결돼 있다.

### 기업 실증 전에 채워야 할 부분

| 격차 | 현재 위험 | 연구 기반 개선 |
|---|---|---|
| 실제 로그 수집·정규화 부재 | 합성 이벤트에서는 맞지만 실제 공급자 로그에서 필드 누락·왜곡 가능 | OCSF 어댑터와 변환 품질 리포트 |
| 단일 이벤트 중심 | 여러 호스트·세션에 걸친 저속 공격을 놓침 | 시간창·엔터티 상관분석과 사건 집계 |
| 규칙·정책이 Python에 고정 | 변경 검토, 이식, 롤백, 승인 이력 관리가 어려움 | Sigma + Cedar/OPA 정책 저장소 |
| 합성 8건 평가 | 정확도 100%가 실제 일반화를 증명하지 않음 | Loghub, OTRF, 공격 재현 로그로 외부 검증 |
| 정적 ATT&CK 매핑 | 프레임워크 변화와 데이터 출처를 추적하기 어려움 | 버전 고정 STIX 스냅샷과 변경 테스트 |
| 설명의 근거성 평가 부재 | 맞는 위험도라도 존재하지 않는 근거를 만들 수 있음 | evidence ID 정확도·인용 완전성 평가 |
| 프롬프트 공격 회귀 세트 부족 | 로그 문자열이 모델 지시로 오인될 수 있음 | 인젝션·비밀유출·과잉거부 테스트 |
| 대응 플레이북 계약 부재 | 실행 기능 추가 시 순서·필수 승인 누락 가능 | CACAO 기반 계획 + 결정론적 검증기 |
| 장기 운영 지표 부족 | 드리프트와 데이터 품질 저하를 뒤늦게 발견 | 소스별 FPR, 보정 오차, MTTD, 검토 수정률 추적 |

## 7. 권장 구현 로드맵

### P0 — 데이터·탐지 기반선

1. `SecurityEvent`와 OCSF 이벤트 사이의 변환 계층을 만든다.
2. 입력마다 원본 해시, 스키마 버전, 수집 시각, 변환기 버전, 누락 필드를 저장한다.
3. Sigma 규칙 로더와 최소 조건 실행기를 추가하고 기존 시나리오 규칙을 Sigma 메타데이터와 연결한다.
4. ATT&CK STIX 컬렉션을 버전 고정한 로컬 스냅샷으로 사용한다.
5. Loghub와 OTRF의 작은 표본을 Docker에서 오프라인 재생하는 평가 하네스를 만든다.

P0 완료 기준:

- 선택한 로그원에서 필수 OCSF 필드 매핑률 95% 이상
- 같은 이벤트 재수집 시 중복 사건 생성 0건
- 정규화 실패가 무시되지 않고 별도 오류 큐로 100% 기록
- 규칙별 precision, recall, FPR과 처리량을 재현 가능한 보고서로 생성

### P1 — 사건 상관분석·정책 검증

1. 사용자, 기기, IP, 세션, 자원 ID를 기준으로 5분·30분·24시간 시간창 집계를 만든다.
2. 단일 경보를 `incident`로 묶고 사건 타임라인과 관련 증거 ID를 생성한다.
3. LLM 입력을 전체 로그가 아닌 선별된 사건 증거 묶음으로 제한한다.
4. Cedar 또는 OPA로 권한·조치 정책을 분리하고 정책 버전과 결정 이유를 감사한다.
5. CACAO의 조사·완화 플레이북 일부를 지원하되 계속 미리보기 모드로 유지한다.

P1 완료 기준:

- 다중 단계 공격 시나리오에서 사건 단위 recall을 이벤트 단위 기준보다 개선
- 모든 LLM 주장에 최소 한 개의 실제 evidence ID 존재
- 금지 조치·순서 위반·승인 누락 테스트 차단률 100%
- 정책 변경 전후 권한 차이를 자동 보고하고 승인 없이 운영 정책 승격 불가

### P2 — LLM 안전성·운영 검증

1. CyberSecEval 2 유형의 프롬프트 인젝션과 데이터 유출 테스트를 프로젝트 이벤트 형식으로 변환한다.
2. 로컬 소형 모델과 외부 모델을 같은 사건 세트에서 비교한다.
3. 모델·프롬프트·규칙·정책 버전을 분석 결과에 함께 기록한다.
4. 장애, 지연, IdP 중단, 저장소 손상, 모델 응답 오류를 주입하는 복구 훈련을 만든다.
5. 분석가 피드백을 정답으로 바로 학습하지 않고 이중 검토된 평가 세트로 승격한다.

P2 완료 기준:

- 프롬프트 공격 성공 0건, 비밀·다른 테넌트 데이터 노출 0건
- 안전장치 적용 후 정상 요청 과잉 거부율 목표치 이하
- LLM 장애 시 규칙 기반 서비스 가용성 유지
- 모델 변경 전 고정 회귀 세트와 그림자 평가 통과

## 8. 비용 없이 가능한 검증 실험

| 실험 | 데이터·도구 | 측정값 | 목적 |
|---|---|---|---|
| 로그 정규화 | [Loghub](https://github.com/logpai/loghub) 소형 표본 | 필드 매핑률, 파싱 오류, 처리량 | OCSF 변환기 검증 |
| Windows 공격 로그 | [OTRF Security-Datasets](https://github.com/OTRF/Security-Datasets) | ATT&CK별 recall·FPR·증거 정확도 | 합성 데이터 편향 축소 |

| 이상탐지 비교 | 규칙, DeepLog류 기준선, 로컬 임베딩 | precision, recall, F1, AUCPR | 미지 패턴 보조 신호의 실효성 |
| LLM 절제 실험 | 규칙만 / LLM만 / 혼합 | 정확도, 보정 오차, 지연, 수정률 | 혼합 구조의 실제 이득 확인 |
| 정책 안전성 | 생성·변형한 허용/금지 플레이북 | 정책 위반 차단률, 정상 계획 보존률 | SOCpilot 방식의 검증기 평가 |
| 프롬프트 공격 | 이벤트 필드에 삽입한 명령·유출 유도 문자열 | 공격 성공률, 과잉 거부율 | 비신뢰 데이터 경계 검증 |

CALDERA와 Atomic Red Team은 반드시 외부와 분리된 실험 환경에서 승인된 대상에만 사용해야 한다. 초기 단계에서는 공개 데이터 재생만으로도 대부분의 파이프라인 검증을 수행할 수 있다.

## 9. 평가 지표 권고

정확도 하나로는 기업 운영 가능성을 판단할 수 없다.

- 탐지 품질: precision, recall, F1, AUCPR, 테넌트·로그원·ATT&CK 기법별 FPR
- 보정 품질: confidence 구간별 실제 적중률, Brier score 또는 ECE
- 조사 품질: 증거 ID precision/recall, 사건 타임라인 완전성, 근거 없는 주장 수
- 운영 품질: MTTD, 검토 완료 시간, P50/P95 지연, 큐 적체, 실패율
- 사람 협업: 분석가 수정량, 판단 뒤집힘 비율, 검토자 간 합치도
- 안전성: 프롬프트 공격 성공률, 데이터 누출 건수, 정책 위반 차단률, 과잉 거부율
- 비용성: 사건당 토큰·CPU 시간, LLM 호출률, 규칙 단계에서 종료된 비율

합격선은 전체 평균뿐 아니라 고위험 시나리오의 최악값으로 관리해야 한다. 특히 `CRITICAL` 대응의 잘못된 자동 허용은 평균 정확도가 높아도 출시 차단 사유로 둔다.

## 11. 최종 제안

다음 개발 단계의 최우선 기능은 `OCSF 정규화 + Sigma 규칙 + 공개 로그 재생 평가`다. 이 조합이 완성돼야 이후 상관분석과 LLM의 실질적 개선 여부를 측정할 수 있다.

당장 피해야 할 작업은 대규모 파인튜닝, 자율 대응 실행, LLM 기반 ATT&CK 자동 확정이다. 현재 연구는 이 세 가지가 실제 로그와 복잡한 사건에서 충분히 신뢰할 수준임을 보여주지 못한다. 먼저 표준 데이터, 재현 가능한 평가, 결정론적 정책 경계를 만든 뒤 LLM을 제한된 업무에서 단계적으로 확대하는 것이 비용과 위험 모두에서 가장 합리적이다.
