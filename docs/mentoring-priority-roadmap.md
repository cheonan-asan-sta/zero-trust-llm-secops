같은 날 인프라 계획을 보완했다. **내구성 있는 신호 수신·처리, 서비스 신원 검증, 별도 접근 집행**을 M3~M5에 연결하고 백업·복원, 경보, 키 관리, AI 호출 제한과 배포 재현성을 완료 기준에 포함한다. 개발·장애 시험은 로컬 Docker Compose로 수행하며 제출일과 기능 동결일은 유지한다.

원래 역할에 맞춰 **인프라 구성·실행·측정은 채희주**가 주담당한다. Compose·네트워크·인증서/키·프록시·관측·스캐너·배포·백업/복원을 직접 실행하고 장애 주입·자원·지연·복구 시간과 원자료를 기록한다. **김택희는 백엔드·앱 지표·기능/상태 검증**을 맡는다. 인가 API·허용 소비/회수·저장 일관성·복원 후 상태를 구현/검증하고 인프라 결과와 대조한다. M6 모델 평가 실행기와 집계는 김택희의 기존 역할로 유지하며, 통합 시험과 교차 재현은 공동 수행한다. 아래 예정 업무의 배정이며 과거 개인 기여를 뜻하지 않는다.

추가로 오픈소스·직접 구현·기존 재사용·상용/관리형 프로그램의 **시험 적용·동일 조건 비교·선정 근거 작성**을 주간 필수 작업에 연결한다. 후보·기한·완료 기준은 [기술 비교 실행 계획](technology-selection-plan.md)의 C01~C10, 상태와 결과는 [선정 대장](technology-decisions/README.md)으로 관리한다. 문서 조사·연결 확인·실제 비교를 구분하며 도입 보류에도 근거를 남긴다.

후속 C02: [HTTP 집행 기록](technology-decisions/C02-http-pep.md)은 기존 인가 API와 위험 관찰 worker를
실제 두 프록시·별도 합성 문서 서버에 연결한다. “위험 신호 처리 후 다음 요청에서 내용 전달 거부”와
직접 접근·위조·재사용·장애를 검증하며, 운영 신원/통신 보호·진행 중 요청 취소·독립 검증은 후속으로 남긴다.

## 이번 수정에서 바꾼 우선순위

11/4 [CA DB·서비스 호스트 복구](ca-db-host-recovery.md)를 I4·I6/C04에 연결한다. CA 전용 DB의
remote_apply 복제·정지 증명 후 승격·새 저장소 재가입·암호화 백업/복원과 최신 보안 상태 대조를
로컬에서 실행한다. 채희주가 실행/측정하고 김택희가 의미 대조·독립 재현한다. 기존 I4의 앱 SQLite
일관된 복원·허용 무효화와 물리 호스트/관리 영역 HA는 별도 미완료 범위로 유지한다.

추가 [CA 프로세스 HA](ca-high-availability.md)는 요청된 가용성 보완으로 로컬 CA 2대·공유 SQL 상태·
DB mTLS·관리 클라이언트 전환과 키 교체의 전체 노드 장벽을 검증한다. 채희주가 구성/장애 주입/측정,
김택희가 상태 의미 대조·독립 재현을 맡는다. DB/호스트 이중화·HSM·유출 사고 복구는 남은 운영 점검이다.

추가 [CA·JWK 자동 교체](authority-key-rotation.md)는 root/issuer·66개 등록 키와 신뢰 이행을 별도 로컬
프로필에서 처리한다. 채희주는 보관/신뢰 배포·구성·실행·장애 측정을, 김택희는 앱 권한 계약 대조와 독립
재현을 맡는다. HSM/운영 HA·전사 미등록 신뢰 배포·사고 복구·anti-rollback을 다음 운영 점검으로 남긴다.

추가 [개인키 자동 교체](private-key-rotation.md)는 C04의 동일 키 갱신 후속으로 명시적으로 적용한다.
채희주는 leaf 키/설정 전환·CA 폐기·서비스/장애 측정을, 김택희는 기존 API/회수 계약 대조와 독립 재현을
담당한다. CA/JWK 서명키 교체·HSM·운영 검토는 다음 점검 항목으로 남기며 학기 전체 완료로 표시하지 않는다.

추가 [C04 인증서 자동화](certificate-automation.md)는 명시된 자동 발급·갱신 요구를 먼저 처리한다.
서비스별 갱신 권한을 업무 권한과 분리하고, 새 지문·서비스 재적용·구 지문 제거와 실제 회수/문서 거부의
근거를 연결한다. 운영 배포/루트 교체/독립 검토를 완료로 소급하지 않는다.

추가 [전체 선택 경로 mTLS](all-hops-mtls.md)는 PEP·core·수집기·관측/경보 네트워크와 관리 조회를
같은 신뢰 경계로 연결한다. 신원과 기존 앱 권한을 별도로 검증하고 실제 위험 신호→회수→문서 거부와
장애 경보·복구의 증거를 묶는다. 단일 호스트 실험이며 운영 CA/실제 IdP·독립 검토는 후속이다.

11/3 후속 [I2 서비스 인증](i2-service-mtls.md)은 C02의 PEP→인가 API에 실제 mTLS를 연결한다.
등록된 인증서 지문과 호출 범위·기존 API 권한을 함께 검사하고 교체/폐기/만료를 시험한다.
운영 TLS 전체·실제 IdP/CA 자동화·백업 복원·멘토 확인 완료와 구분한다.

1. 프로젝트 범위와 제로트러스트 요소를 먼저 확정하고 피드백별 확인 항목을 관리한다.
2. 인증·기기 신호의 권한 분리와 세션 평가용 데이터를 확보한다.
3. 신호를 내구성 있게 저장한 뒤 별도 처리기로 관련 세션을 자동 재평가하고 재시작·재전송을 시험한다.
4. GuardDuty의 공식 EventBridge 형식 입력을 로컬에서 검증하고 서비스 간 인증·통신 보호·키 회전을 연결한다.
5. 별도 업무 서비스에 집행을 연결하고 우회 차단·승인·장애 복구·백업 복원 후 회수 상태를 시험한다.
6. 규칙·판단 전용 모델·생성형 LLM의 역할을 나누고 품질·미탐·비용·지연을 비교해 멘토에게 제시한다.
7. 11월 29일 기능을 동결하고 보고서·인스타·발표·시연 자료를 마무리한다.

이전 안의 별도 인증 서버 도입은 핵심 피드백 증거 확보 이후의 확장 후보로 옮긴다. 실제 기업 IdP·EDR·네트워크 전체 분리, 신규 패킷 탐지 엔진과 화면 장식은 필수 피드백 작업보다 먼저 진행하지 않는다. 모델 비교는 M6의 검증 작업으로 진행하며, 후보 수를 늘리기 위해 M3·M4·M5를 지연하지 않는다. 실제 인증 연동이 없어도 된다는 뜻은 아니며, 기업 운영 검증에서는 남은 항목으로 유지한다.

### GuardDuty와 실제 연동의 구분

GuardDuty는 finding을 EventBridge 이벤트로 전달하며, 새 finding과 기존 finding 갱신의 통지 방식이 다르다. 로컬 어댑터는 공식 `source`, `detail-type`, 계정·지역·시각·finding 본문 구조를 검사한다. 이벤트 ID와 finding ID·갱신 시각을 구분해 중복과 갱신을 처리한다. 이 설명과 형식은 [AWS 공식 문서](https://docs.aws.amazon.com/guardduty/latest/ug/guardduty_findings_eventbridge.html)를 기준으로 한다.

문자열 `source=aws.guardduty`만으로 출처를 신뢰하지 않는다. 서명된 로컬 송신자 등 수신 경계 인증과 테넌트·주체·자원 매핑을 별도로 검사한다. IP 하나만으로 세션을 연결하거나 경보가 없다는 이유로 정상 인증을 인정하지 않는다. 연결 근거가 부족한 경보는 조사 대상으로 남긴다. 경보 갱신 지연을 정상 상태의 근거로 사용하지 않는다.

이번 비용 없는 범위의 완료 명칭은 **GuardDuty 공식 형식 로컬 호환 검증**이다. AWS 서비스에서 실제로 수신한 것으로 기록하지 않는다. 실제 연결은 별도 운영 항목이며 대상 계정은 기존 지정 계정 `172585182454`다. 이 계획은 AWS 자원 생성·GuardDuty 활성화·배포·과금 호출을 지시하지 않는다.

### 대응 자동화와 안전장치의 범위

정책에 따른 접근 거부·허용 회수는 자동으로 수행하되 계정 비활성화·기기 격리 등 고위험 대응은 이번에는 모의 조치로 한정한다. 해당 모의 조치에는 대상·행위·승인자 역할·유효기간·버전·단일 사용 조건을 검사하고 실행 결과를 기록한다. 미승인 조치는 검토 상태로 유지하며 임의로 성공 처리하지 않는다. 회수된 세션을 자동으로 되살리는 방식으로 복구하지 않는다.

## 인프라 보완 계획과 완료 기준

### 현재 기준선과 범위

현재 Compose는 단일 앱과 영속 볼륨을 사용한다. 비관리자 실행·읽기 전용 파일시스템·권한 제거·상태 확인을 재사용한다. 앱의 OIDC·역할·테넌트 검사, 수집기 서명·키 회전, 메트릭과 연동 아웃박스도 기존 기능이다. 지속 수신·분리된 처리기·서비스 간 인증·독립 PEP·경보 수집·백업 복원 훈련은 추가 작업이며 기존 기능과 구분해 기록한다.

학기 필수 구현은 로컬의 단일 호스트 Compose 범위로 제한한다. 수신·처리 분리에는 저장 경계와 서비스별 권한을 명시하고, 기존 아웃박스의 이벤트 계약·재시도 기능을 재사용할 수 있는지 검토한다. 송신용 아웃박스가 수신 큐까지 이미 구현했다는 의미는 아니다. SQLite를 유지하는 동안 쓰기 소유자와 트랜잭션 경계를 고정하며 여러 프로세스의 JSONL 공유 쓰기는 피한다. PostgreSQL 전환·대규모 메시지 플랫폼·Kubernetes·전체 서비스 메시·다중 지역 고가용성은 후속 운영 후보로 둔다.

위 PostgreSQL 전환은 앱 상태 저장소에 대한 후속 후보이며, [CA 프로세스 HA](ca-high-availability.md)의
CA 전용 PostgreSQL과 구분한다. CA DB 적용으로 앱 SQLite 전환이나 다중 호스트/지역 HA를 완료하지 않는다.

### 자체 대시보드와 오픈소스 선정

운영 대시보드는 기존 `app/static/` 화면을 확장해 자체 개발한다. 세션 상태·판단 근거·회수·접근 집행·승인·감사 이력과 운영 지표를 한 흐름으로 연결한다. Grafana·Perses는 학기 필수 도입에서 제외한다. 화면 개발과 메트릭 저장·수집·경보 기능의 재사용은 별도로 판단한다. 조회는 인증된 서버 API에서 역할·테넌트 범위를 제한하고, 브라우저에 관리용 수집 자격증명·모델 API 키를 전달하지 않는다. 화면 새로고침으로 유료 분석을 자동 실행하지 않는다.

추가 오픈소스는 아직 설치·채택하지 않았다. 아래 항목은 우선 평가할 후보이며 각 분야 최고라는 성능 순위가 아니다. 비교는 기능 공백을 채우는 소수 후보로 제한하고 동일한 입력·버전·권한·장애 조건에서 검증한다.

| 영역과 후보 | 이번 학기 판단·시점 | 선정 조건 |
|---|---|---|
| 메트릭·경보: Prometheus+Alertmanager / VictoriaMetrics+vmalert+Alertmanager | C01·I5, 11/15 양 구성 시험·잠정 선정, 11/22 확정 | 기존 메트릭 재사용, 동일 보존·규칙·인증에서 경보 발생/해제·수집 중단·자원·지연 비교. 자체 화면은 제한된 서버 API로 조회 |
| HTTP 접근 집행: NGINX `auth_request` 또는 Envoy `ext_authz` | I2·I3 우선 비교, 11/9~11/15 인가 계약·11/16~11/22 적용 | 한 후보를 선정해 직접 접근·헤더 위조·만료·회수·인가 서버 장애 시 거부 검증. 단일 사용 허용의 소비·재시도 의미와 원래 자원/행위 보존 확인 |
| 공급망 검사: Syft·Grype 또는 Trivy | I8 우선 비교, 11/2~11/8 초기 검사·11/22 재현 절차 | 같은 이미지의 패키지·취약점 근거·오탐·지원 범위 비교. 비밀값/설정 검사 공백도 확인. 배포 출처·보안 공지·서명·지문과 검사 DB 버전을 확인하고 결과 재현 |
| 인증서 자동화: step-ca | I2·I6 조건부 후보, 기본 mTLS 경로 안정 후 검토. 학기 필수 범위에 추가하지 않음 | 서비스 인증서 발급·갱신 자동화가 필요할 때만 평가. CA 키 보호·발급 권한·갱신 실패·기존 연결·폐기 후 접근 거부를 별도로 검증 |
| 기기 상태 수집: osquery | M3 후속 후보, 기본 수신·신호 권한 분리·집행 검증 후 | 허용된 실험 환경의 필요한 항목만 수집하고 플랫폼·권한·시각·기기 매핑·출처를 기록. 변조·누락·오래된 신호를 정상으로 해석하지 않음 |
| 메시지 브로커: NATS JetStream 등 | I1의 현 단일 호스트 구현으로 충분한 동안 보류 | 처리기 확장·분리 배포 요구가 확인될 때 검토. 내구 접수·확인·재전달·중복 방지·부하 제한을 종단 시험. 설치 자체가 유실 방지나 단일 처리의 증거는 아님 |

Prometheus·Alertmanager는 [메트릭](https://prometheus.io/docs/introduction/overview/)·[경보](https://prometheus.io/docs/alerting/latest/alertmanager/) 공통 기능을 재사용할 후보다. 접근 집행은 [NGINX](https://nginx.org/en/docs/http/ngx_http_auth_request_module.html)와 [Envoy](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/ext_authz_filter)의 인가 연결 방식으로 비교한다. [Syft·Grype](https://oss.anchore.com/docs/)와 Trivy는 지원 범위가 같다고 가정하지 않는다. Trivy는 [2026년 3월 공급망 침해 공식 공지](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23)의 영향 버전·배포 경로·기간을 확인하고 검증된 배포물로만 평가한다. 이 이력만으로 다른 스캐너가 자동으로 안전하다고 결론 내리지 않는다.

[step-ca](https://smallstep.com/docs/step-ca/)는 TLS 인증서 관리 후보다. 기본 [폐기 방식](https://smallstep.com/docs/step-ca/revocation/)은 갱신을 막고 만료를 기다리므로 요청별 서비스 인가·폐기 확인·세션 회수는 별도로 유지한다. 기존 Ed25519 수집기 서명과 TLS 서비스 인증서의 역할을 구분한다. [osquery](https://github.com/osquery/osquery)는 운영체제 관측 도구이며 기기 무결성의 독립 증명이나 EDR 전체를 대신하지 않는다. 컨테이너 관측을 호스트 상태 증명으로 기록하지 않는다. 실제 도입·호스트 설치·수집 항목 확대는 후속 작업 범위로 분리한다. [JetStream](https://docs.nats.io/nats-concepts/jetstream/consumers)도 재전달에 대한 애플리케이션 중복 방지와 상태 원자성을 대체하지 않는다.

채희주는 자체 화면 구성·신뢰 경계·도구 설치/설정/실행·인프라 성능/자원 측정·원자료/집계·선정 근거를 주담당한다. 김택희는 API·입력/응답 계약·앱 지표·인가 로직·기능/상태 시험과 상대 결과 검증을 맡는다. C02 프록시 운용은 채희주, 인가 API와 허용 소비/회수는 김택희가 맡고 집행 경로는 공동 통합한다. 기존 화면 확장과 교차 검증도 공동 수행한다. 조건부 후보는 필요 판정 후 진행하며 11/29 이후 새 도구를 추가하지 않는다.

위 후보는 [기술 비교 실행 계획](technology-selection-plan.md)에 통합한다. C01~C03은 두 대안을 실제 적용해 비교하고 C04~C09는 필요 판정 후 조건부 시험 또는 문서 비교·보류 근거를 남긴다. C10은 기존 M6 실제 모델 평가와 연결한다. 상용/관리형 프로그램은 공개 문서·허용된 제공 환경으로 비교하고 새 계정·유료 계약·외부 배포가 필요한 경우 미측정 조건을 명시한다. 모든 영역에서 기존 구현 유지와 직접 개발도 대안이다. 비교 완료는 원자료·선정 이유·탈락/보류 이유와 상대 재현으로 판정한다.

아래는 예정된 검증 구조다. 서비스 분리는 인증·권한 검사를 보완하며 대체하지 않는다.

```text
서명 수집기 → 인증된 수신기 → 내구 저장 → 재평가 처리기 → 정책 엔진
                                                      ↓ 허용·회수 상태
접근 요청 → 독립 PEP → 보호 업무 자원
                  ↘ 정책·세션·행위·허용 유효성 검사
각 서비스 → 권한이 제한된 감사·메트릭 수집 → 자체 대시보드·경보
조사 보조 → 제한된 AI 호출 계층 → 허용된 모델 API 또는 로컬 모델
```

### 주간 검증과 운영 배포 경계

11/8까지 서비스별 소유자·허용 통신·키 접근표와 처리 지연·신호 최대 나이·대기량·복구 목표를 수치로 정한다. 실제로 측정하지 않은 수치를 성능 목표 달성으로 표시하지 않는다. I1~I3 핵심 경로와 필수 안전 시험이 미달하면 모델 수 확대·대시보드 장식·새 플랫폼 도입을 이월한다. 지원 항목은 기존 기능을 재사용한 최소 범위로 구현하고 새 업무 시스템 전체 구축으로 확대하지 않는다.

11/29 독립 통합 평가는 서비스 중단·통신 단절·인증서 만료·키 폐기·저장 실패·오래된 백업·AI 오류를 주입해 수행한다. 정상 업무 영향, 새 허용 발급·기존 허용 소비·회수 상태, 감사·경보 결과를 따로 기록한다. 구성을 추가한 것만으로 실제 서비스 인증·인프라 격리·복구가 검증됐다고 처리하지 않는다.

기존 Lambda 템플릿은 현재 로컬 세션 운영 기능의 완성된 운영 배포 구성이 아니다. 11/22 정적 구성 점검에서 앱 환경·OIDC/서비스 인증·테넌트 권한·영속 상태·공유 저장·상시 처리의 차이를 대장에 남긴다. 함수 URL의 AWS IAM 인증이나 감사용 DynamoDB만으로 이 조건을 충족했다고 처리하지 않는다. 로컬 전용 경로의 production 비활성화는 유지한다. 운영 배포 설계와 실제 배포는 후속 검증이며 이번 계획에 AWS 자원 생성은 포함하지 않는다.

기준 자료는 [NIST SP 800-207A](https://csrc.nist.gov/pubs/sp/800/207/a/final)의 서비스 신원·세분화된 정책, [Docker Compose 네트워크](https://docs.docker.com/compose/how-tos/networking/), [AWS 보안 설계 원칙](https://docs.aws.amazon.com/wellarchitected/latest/framework/sec-design.html)을 참고한다. 특정 제품 설치를 표준 준수나 운영 완료의 증거로 사용하지 않는다.

## 작업별 인공지능 모델 비교

연구 질문은 **안전 조건과 탐지 품질을 유지하면서 작업별 모델 선택으로 총비용과 처리 지연을 줄일 수 있는가**다. Jev·Laya는 짧은 분류·선택형 질문 후보이고, 생성형 LLM은 세션 해석과 설명 후보다. 임베딩·재정렬·이상탐지는 별도의 작업과 데이터가 있을 때만 검토한다. 후보의 공개 성능 수치를 우리 보안 데이터의 성능으로 사용하지 않는다.

| 역할 | 검토할 예시 후보 | 비교할 작업과 주의점 | 적용 순위 |
|---|---|---|---|
| 정확한 조건 검사 | 기존 코드·규칙, AI 미사용 | 서명·만료·권한·테넌트·허용 토큰 검사. 모델로 대체하지 않음 | 필수 기준선 |
| 짧은 판단과 분석 경로 선택 | Jev, Laya multilingual·typed-decisions, TF-IDF+로지스틱 회귀 기준선 | 이벤트 유형·조사 우선순위·추가 분석 필요 여부. 소수 선택지와 정보 부족 항목, 한국어·영문 로그 혼합에서 검증 | 우선 비교 |

위 역할 배치는 적용 가설이다. 생성형 후보 전부와 임베딩·이상탐지까지 학기 필수 기능으로 추가하지 않는다. Laya의 기본 모델과 해당 과제에 맞춰 학습한 모델은 서로 다른 실험으로 기록한다. 다국어 체크포인트라고 한국어 보안 분류 품질이 입증된 것은 아니다. 공식 카드에 제시된 무학습 성능·과신·입력 길이·선택지 순서의 한계를 검증 항목에 포함한다.

### 선정 절차와 호출 경로

11월 8일까지 생성형 기준 모델 1개와 타 공급자 비교 모델 1개를 고르고, 동일한 분류 작업에 Jev·Laya·단순 기준선을 비교한다. 계정 접근이나 실행 자원이 없는 후보는 사유와 함께 미측정으로 남긴다. 첫 단계에는 실제 허용·회수에 영향을 주지 않는 관찰 모드로 결과만 수집한다. 수집·정책·집행 구현을 먼저 진행하며 모델 수 확대는 초기 후보가 의미 있는 차이를 보일 때만 한다.

```text
인증된 신호 → 코드·정책의 필수 검증 → 정책 엔진의 허용·재인증·회수
                         └→ 조사 보조 경로
                             간단한 분류: 판단 모델 또는 경량 기준선
                             복잡·불명·정책 충돌: 생성형 LLM과 필요 시 사람 검토
                             설명·조사 권고 → 운영자에게 제공
```

모델이 정상이라고 답하거나 모델끼리 동의해도 필수 신호 검증·위험 규칙·재인증·승인을 건너뛰지 않는다. 판단 모델은 최종 접근 권한을 발급하지 않고, 고위험·정보 부족·명시적 정책 위반을 분석 생략 대상으로 만들지 않는다. 불일치·시간 초과·형식 오류는 기록 후 규칙 경로와 검토 상태로 복구한다.

### 공정한 비교와 채택 기준

- 같은 작업끼리 비교한다. 분류는 Jev·Laya·경량 기준선·생성형 LLM에 공통 질문·선택지·입력을 주고, 한국어 설명 품질은 생성형 LLM끼리만 비교한다. Jev·Laya의 텍스트 비생성 자체를 설명 실패로 계산하지 않는다.
- 모델 ID·버전 또는 가중치 지문, API 지역·추론 설정·입력 상한·프롬프트 지문을 기록한다. 동등한 정보 범위를 제공하며 모델별 토큰 수는 따로 측정한다. 입력 잘림·번역 여부도 남긴다.
- 세션 기준으로 개발·보정·평가를 분리한다. 단순 분류기 학습과 확률 보정은 개발/보정 데이터에만 수행한다. 기존 최소 세션 12개는 시연 최소치이며 학습·보정이나 일반화 주장에 충분하다고 간주하지 않는다.
- 분류 정확도·오탐·미탐·근거 없는 주장·JSON 준수·오류를 집계하고 확률은 Brier score·신뢰도 구간별 실제 정답률로 점검한다. 정보 부족·분포 밖·질문 표현 변경·선택지 순서·로그 내 지시문을 시험한다.
- 모델 단독 추론 지연과 네트워크 포함 P50·P95, 직렬/병렬 호출의 전체 지연을 구분한다. 워밍업·콜드 시작·입력 길이·반복 횟수·하드웨어를 기록하고 공급사 발표 수치를 서로 다른 조건에서 직접 비교하지 않는다.
- API 입력·출력·추론·캐시·재시도·실패·두 번째 모델 호출과 현지 실행의 자원 사용을 포함해 사건당 총비용을 계산한다. 자체 실행 모델의 API 요금이 없다는 것을 운영비 0원으로 쓰지 않는다. 실행별 금액·요청·토큰·시간 상한을 설정해 초과 시 중단한다.
- 종단 구성은 규칙 전용, 규칙+생성형 LLM, 규칙+판단 모델+선택적 LLM을 비교한다. 분석을 생략한 사례도 정답 평가하고 일부를 무작위로 재검토해 누락을 측정한다. 같은 사건에서 여러 모델의 답은 독립 표본으로 세지 않는다.
- 채택은 평가 전에 정한 미탐·정상 업무 유지·설명 품질·비용·지연 기준을 모두 만족할 때만 한다. 임계값은 개발셋에서 정하고 평가셋에 맞춰 바꾸지 않는다. 작은 표본에서는 건수·불확실성을 제시하고 상시 사용의 우월성을 단정하지 않는다.

추가 후보를 넣을 조건은 현재 후보가 품질·한국어·라이선스·데이터 처리·응답시간·비용 중 한 가지 요구를 충족하지 못하는 경우다. 단순 모델도 기준을 만족하면 선택할 수 있고, 새 모델이 유리하지 않으면 미채택 결과도 보고한다. 최종 산출물은 후보 목록보다 **역할별 채택/미채택 근거와 재현 가능한 비교 결과**다. 상세 후보와 공식 자료는 [모델 검토 목록](model-candidate-review.md)을 따른다.

## 시험과 평가 기준

### 평가 데이터

11월 1일까지 시나리오 명세와 공개 자료 후보를 정리하고, 11월 15일까지 기존 표본과 다른 공개 계정·인증 로그 출처 1개 이상을 추가 확보한다. 접근 조건·라이선스·세션 연결 가능성을 검토하고 사용 가능한 원본·변환 이력을 남긴다. 확보하지 못한 경우 합성 자료로 조용히 대체해 완료 표시하지 않고 원인과 대안을 대장에 기록한다.

11월 22일까지 **독립 세션 12개 이상, 정상 6개·위협 6개 이상**을 목표로 평가셋을 동결한다. 기존 공개 원본 12건은 유지하고, 그 원본이 실제 종단 세션 공격의 증거인 것처럼 바꾸지 않는다. 공개 원본, 공개 자료에서 재구성한 세션, 합성·장애 주입 사례를 각각 표시한다.

같은 세션의 이벤트가 개발셋과 평가셋에 나뉘지 않도록 개발 8개 이상·독립 평가 4개 이상으로 분리한다. 평가셋에도 정상·위협이 모두 포함되게 하며 기대 결과를 시험 전에 확정한다. 평가 후 정책을 조정하면 변경과 재평가 이력을 남긴다. 공개 자료의 출처·라이선스·원본 해시·변환 절차·라벨 근거를 기록하고 작은 표본의 결과를 기업 전체 성능으로 일반화하지 않는다.

### 공통 완료 관찰값

- 정상: 신뢰된 정상 신호가 모인 경우에만 허용하고 정당한 접근·재인증의 성공과 불필요한 보류·차단을 구분한다.
- 위험: 침해·인증 실패·권한 위반 시 관련 허용을 회수하고 다음 업무 자원 접근이 거부되는지 확인한다. 무관한 세션은 유지한다.
- 입력: 위조·범위 초과·만료·중복·지연·순서 역전·연결 불명·테넌트 불일치를 각각 기록한다.
- 집행: 자원·행위·운영자 범위, 단일 사용, 동시 접근, 통제 지점 우회와 승인 만료를 검사한다.
- 장애: 수집 중단·저장 실패·프로세스 재시작에서 근거 없이 허용하거나 성공 이력을 만들지 않는다.
- 인프라: I1~I8의 접수 내구성·서비스 신원·우회 차단·복원 후 허용 무효화·키 폐기·경보·AI 한도·배포 복구 결과를 피드백별 증거에 연결한다.
- 기술 선정: C01~C03 실제 비교·선정 근거·통합 회귀, C04~C09 시험/문서 비교/보류 이유, C10 모델 독립 평가를 기록한다. 설치·연결 성공만으로 비교 완료를 표시하지 않는다.
- 측정: 이벤트 발생·수신·판단·집행 시각과 측정 구간을 구분한다. 로컬 수신→판단·접근 거부 지연과 정상 허용·불필요 보류·공격 차단 결과를 보고한다.
- AI: 실제 API를 호출하지 않은 모의 비교는 연결·실패 복구 시험으로만 표기한다. 실제 모델의 정확도·비용·지연을 입증한 것으로 기록하지 않는다.
- 회귀: 기존 시험을 유지하고 변경된 기능에 필요한 시험과 Docker 종단 시연을 추가한다. 시험 수의 증가 자체를 성능 개선으로 해석하지 않는다.

## 피드백 완료 판정과 매주 운영

상태는 `미착수`, `진행`, `로컬 검증 완료`, `외부 확인 대기`, `범위 제외 검토`로 관리한다. 각 항목에는 담당자·목표일·코드/문서·시험 결과·화면/영상·남은 한계·멘토 확인 결과를 연결한다. 현재 계획 수립만으로 완료 표시하지 않는다.

피드백에 대한 팀 조치는 범위·구현 또는 검토 결론·재현 가능한 증거가 모두 있을 때 완료로 판정한다. 범위 제외는 근거를 준비했다는 이유만으로 멘토가 수용했다고 처리하지 않는다. 실제 GuardDuty·기업 IdP·EDR 연동과 멘토의 최종 수용 여부는 별도 확인 항목으로 유지한다. 따라서 로컬 계획을 모두 마쳐도 **기업 실환경 검증이나 멘토 승인까지 100% 완료**했다고 표현하지 않는다.

매주 시작할 때 피드백 대장에서 최우선 미해결 항목과 완료 기준을 고른다. 주중에는 구현과 독립 재현을 병행하며, 주말에는 달성·미달성·원인·다음 주 이월을 기록한다. 피드백 필수 시험이 미달하면 부가 기능을 시작하지 않는다. 11월 29일 이후에는 새 기능 대신 오류 수정·평가·제출 준비를 우선한다.

주간 보고서에는 문제·멘토링 연결·변경 전후·시험 조건과 실제 결과·한계·다음 조치를 남긴다. 인스타는 같은 증거에서 문제 한 가지와 변화 한 가지를 골라 5장으로 설명한다. 모의 입력·모의 AI·로컬 호환 검증 표시는 화면과 본문에 함께 남긴다. 게시나 멘토에게의 발송은 팀이 별도로 수행한다.

## 비용과 외부 검증 경계

개발·기능 회귀시험은 로컬 Docker와 규칙 모드를 기본으로 한다. 사용자가 허용한 유료 모델 API는 비교 실험에서 사용할 수 있다. 실행별 금액·요청·토큰·시간 상한과 데이터 범위를 기록하고, 기존 테스트나 화면 새로고침이 예고 없이 유료 호출을 만들지 않게 분리한다. 이 계획 수정에서는 실제 모델 호출·설치·계정 설정을 수행하지 않았다. AWS 리소스 생성·배포와 GitHub 업로드는 하지 않는다. 시험 종료 시 이번에 만든 컨테이너·임시 키를 정리하고 Docker가 원래 중지 상태였으면 그 상태로 복원한다.

외부 API에는 비교용 합성·허용된 공개 로그를 우선 사용하고 비밀값·실사용자 식별정보를 제거한다. 계정별 사용 가능 모델·보존·학습 사용·데이터 지역과 라이선스를 확인한다. 실제 기업 서비스 연결은 여전히 별도 운영 검증이며, 모의 시험을 실제 모델 또는 기업 운영 완료로 바꾸지 않는다.
