# 멘토링 피드백 우선 주간 실행 계획

수정일: 2026년 10월 29일 · 구현 기준: `aitest` v0.17.0 (`7f23fee`) · 피드백 기준: 2026년 10월 2일 기업 멘토링 팀 기록

남은 개발은 멘토링에서 지적한 **인증 이후 세션 검증, 실시간 입력, 안전한 대응 집행과 검증 근거**를 먼저 해결한다. 새 기능 수나 버전 수보다 피드백별 완료 증거를 우선한다. 이번 문서 수정은 계획 변경이며 아래 예정 기능을 구현 완료로 바꾸지 않는다.

최종 제출은 **12월 7~13일로 잠정 가정**하고 12월 6일까지 제출 가능한 상태를 만든다. 공식 제출일과 다음 멘토링 일정은 11월 1일까지 팀이 확인한다. 아래 날짜는 실행 일정이며 기존 `week03`~`week14`의 기능 분류를 실제 학사 주차로 해석하지 않는다.

## 이번 수정에서 바꾼 우선순위

1. 프로젝트 범위와 제로트러스트 요소를 먼저 확정하고 피드백별 확인 항목을 관리한다.
2. 인증·기기 신호의 권한 분리와 세션 평가용 데이터를 확보한다.
3. 위험 신호 수신 후 관련 세션을 자동 재평가한다.
4. GuardDuty의 공식 EventBridge 형식 입력을 로컬에서 검증한다.
5. 별도 업무 서비스에 집행을 연결하고 대응 범위·중복·만료·장애를 시험한다.
6. AI 보조 역할, 정상 업무 유지와 공격 대응 결과를 구분해 평가하고 멘토에게 제시한다.
7. 11월 29일 기능을 동결하고 보고서·인스타·발표·시연 자료를 마무리한다.

이전 안의 별도 인증 서버 도입은 핵심 피드백 증거 확보 이후의 확장 후보로 옮긴다. 실제 기업 IdP·EDR·네트워크 전체 분리, 신규 패킷 탐지 엔진, 추가 LLM 모델과 화면 장식은 필수 피드백 작업보다 먼저 진행하지 않는다. 실제 인증 연동이 없어도 된다는 뜻은 아니며, 기업 운영 검증에서는 남은 항목으로 유지한다.

## 현재까지 완료한 기준선

- v0.15 이전: 규칙·선택적 AI 분석, OCSF·Sigma, 공개 고정 표본 12건, 케이스와 연동 아웃박스, API 인증·역할·테넌트 격리. 멘토링 이후 신규 성과로 계산하지 않는다.
- v0.16: 세션 상태·버전·이력, 자원 정책, 단기·단일 사용 허용, 이벤트별 재평가·회수와 로컬 모의 PEP의 HTTP 허용·거부.
- v0.17: 수집기 Ed25519 서명·범위·신선도, 현재 재인증 요청에 연결한 새 서명, 키 폐기·회전 후 기존 허용 거부.
- 기존 검증 기록: 2026년 10월 27일 로컬·Docker 177건 통과. 이번 계획의 미래 검증 결과나 실환경 성능으로 재사용하지 않는다.

현재 제로트러스트 API는 local·test 전용이다. 상시 수집, 여러 관련 세션의 자동 재평가, 실제 GuardDuty 수신, 실제 사용자 MFA·기기 증명, 별도 업무 서비스의 접근 집행은 아직 완료되지 않았다. 상세 기준선은 [구현 명세](zero-trust-operations.md)에 있다.

### GuardDuty와 실제 연동의 구분

GuardDuty는 finding을 EventBridge 이벤트로 전달하며, 새 finding과 기존 finding 갱신의 통지 방식이 다르다. 로컬 어댑터는 공식 `source`, `detail-type`, 계정·지역·시각·finding 본문 구조를 검사한다. 이벤트 ID와 finding ID·갱신 시각을 구분해 중복과 갱신을 처리한다. 이 설명과 형식은 [AWS 공식 문서](https://docs.aws.amazon.com/guardduty/latest/ug/guardduty_findings_eventbridge.html)를 기준으로 한다.

문자열 `source=aws.guardduty`만으로 출처를 신뢰하지 않는다. 서명된 로컬 송신자 등 수신 경계 인증과 테넌트·주체·자원 매핑을 별도로 검사한다. IP 하나만으로 세션을 연결하거나 경보가 없다는 이유로 정상 인증을 인정하지 않는다. 연결 근거가 부족한 경보는 조사 대상으로 남긴다. 경보 갱신 지연을 정상 상태의 근거로 사용하지 않는다.

이번 비용 없는 범위의 완료 명칭은 **GuardDuty 공식 형식 로컬 호환 검증**이다. AWS 서비스에서 실제로 수신한 것으로 기록하지 않는다. 실제 연결은 별도 운영 항목이며 대상 계정은 기존 지정 계정 `172585182454`다. 이 계획은 AWS 자원 생성·GuardDuty 활성화·배포·과금 호출을 지시하지 않는다.

### 대응 자동화와 안전장치의 범위

정책에 따른 접근 거부·허용 회수는 자동으로 수행하되 계정 비활성화·기기 격리 등 고위험 대응은 이번에는 모의 조치로 한정한다. 해당 모의 조치에는 대상·행위·승인자 역할·유효기간·버전·단일 사용 조건을 검사하고 실행 결과를 기록한다. 미승인 조치는 검토 상태로 유지하며 임의로 성공 처리하지 않는다. 회수된 세션을 자동으로 되살리는 방식으로 복구하지 않는다.

## 시험과 평가 기준

### 평가 데이터

11월 1일까지 시나리오 명세와 공개 자료 후보를 정리하고, 11월 15일까지 기존 표본과 다른 공개 계정·인증 로그 출처 1개 이상을 추가 확보한다. 접근 조건·라이선스·세션 연결 가능성을 검토하고 사용 가능한 원본·변환 이력을 남긴다. 확보하지 못한 경우 합성 자료로 조용히 대체해 완료 표시하지 않고 원인과 대안을 대장에 기록한다.

11월 22일까지 **독립 세션 12개 이상, 정상 6개·위협 6개 이상**을 목표로 평가셋을 동결한다. 기존 공개 원본 12건은 유지하고, 그 원본이 실제 종단 세션 공격의 증거인 것처럼 바꾸지 않는다. 공개 원본, 공개 자료에서 재구성한 세션, 합성·장애 주입 사례를 각각 표시한다.

같은 세션의 이벤트가 개발셋과 평가셋에 나뉘지 않도록 개발 8개 이상·독립 평가 4개 이상으로 분리한다. 평가셋에도 정상·위협이 모두 포함되게 하며 기대 결과를 시험 전에 확정한다. 평가 후 정책을 조정하면 변경과 재평가 이력을 남긴다. 공개 자료의 출처·라이선스·원본 해시·변환 절차·라벨 근거를 기록하고 작은 표본의 결과를 기업 전체 성능으로 일반화하지 않는다.

### 공통 완료 관찰값

- 정상: 신뢰된 정상 신호가 모인 경우에만 허용하고 정당한 접근·재인증의 성공과 불필요한 보류·차단을 구분한다.
- 위험: 침해·인증 실패·권한 위반 시 관련 허용을 회수하고 다음 업무 자원 접근이 거부되는지 확인한다. 무관한 세션은 유지한다.
- 입력: 위조·범위 초과·만료·중복·지연·순서 역전·연결 불명·테넌트 불일치를 각각 기록한다.
- 집행: 자원·행위·운영자 범위, 단일 사용, 동시 접근, 통제 지점 우회와 승인 만료를 검사한다.
- 장애: 수집 중단·저장 실패·프로세스 재시작에서 근거 없이 허용하거나 성공 이력을 만들지 않는다.
- 측정: 이벤트 발생·수신·판단·집행 시각과 측정 구간을 구분한다. 로컬 수신→판단·접근 거부 지연과 정상 허용·불필요 보류·공격 차단 결과를 보고한다.
- AI: 실제 API를 호출하지 않은 모의 비교는 연결·실패 복구 시험으로만 표기한다. 실제 모델의 정확도·비용·지연을 입증한 것으로 기록하지 않는다.
- 회귀: 기존 시험을 유지하고 변경된 기능에 필요한 시험과 Docker 종단 시연을 추가한다. 시험 수의 증가 자체를 성능 개선으로 해석하지 않는다.

## 피드백 완료 판정과 매주 운영

상태는 `미착수`, `진행`, `로컬 검증 완료`, `외부 확인 대기`, `범위 제외 검토`로 관리한다. 각 항목에는 담당자·목표일·코드/문서·시험 결과·화면/영상·남은 한계·멘토 확인 결과를 연결한다. 현재 계획 수립만으로 완료 표시하지 않는다.

피드백에 대한 팀 조치는 범위·구현 또는 검토 결론·재현 가능한 증거가 모두 있을 때 완료로 판정한다. 범위 제외는 근거를 준비했다는 이유만으로 멘토가 수용했다고 처리하지 않는다. 실제 GuardDuty·기업 IdP·EDR 연동과 멘토의 최종 수용 여부는 별도 확인 항목으로 유지한다. 따라서 로컬 계획을 모두 마쳐도 **기업 실환경 검증이나 멘토 승인까지 100% 완료**했다고 표현하지 않는다.

매주 시작할 때 피드백 대장에서 최우선 미해결 항목과 완료 기준을 고른다. 주중에는 구현과 독립 재현을 병행하며, 주말에는 달성·미달성·원인·다음 주 이월을 기록한다. 피드백 필수 시험이 미달하면 부가 기능을 시작하지 않는다. 11월 29일 이후에는 새 기능 대신 오류 수정·평가·제출 준비를 우선한다.

주간 보고서에는 문제·멘토링 연결·변경 전후·시험 조건과 실제 결과·한계·다음 조치를 남긴다. 인스타는 같은 증거에서 문제 한 가지와 변화 한 가지를 골라 5장으로 설명한다. 모의 입력·모의 AI·로컬 호환 검증 표시는 화면과 본문에 함께 남긴다. 게시나 멘토에게의 발송은 팀이 별도로 수행한다.

## 비용과 외부 검증 경계

개발·시험은 로컬 Docker와 규칙 모드를 기본으로 한다. AWS 리소스와 유료 API는 호출하지 않고 GitHub에 업로드하지 않는다. 외부 형식은 공개 문서를 기준으로 로컬에서 재생한다. 시험 종료 시 이번에 만든 컨테이너·임시 키를 정리하고 Docker가 원래 중지 상태였으면 그 상태로 복원한다.

실제 서비스 연결·실제 모델 품질 평가가 필요해지면 비용·권한·데이터·대상·성공 기준을 확정한 별도 검증으로 관리한다. 현재 미구현인 작업의 비용을 피하기 위해 모의 시험을 실제 운영 완료로 바꾸지 않는다.
