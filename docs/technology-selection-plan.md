# 기술 비교와 선정 실행 계획

11/8 후속 [개인키 회차·자원 측정 구간 격리](rekey-and-resource-measurement-isolation.md): PR47 첫 병합 후 개인키12개 중단과 자원 수집2건 실패를 보존한다. 시험은 동일 pending키/정확히1세대 증가를 검사하고, 관측v2는 준비·실제 부하·의도적 장애 구간을 구분한다. 로컬22/37·Linux2577·소유 자원0이며 새 정확한 head/병합 후 CI는 후속 PR을 따른다. C01/C02 로컬 조건부·C03 보류·독립 인수/3주차 전체 미완료는 유지한다.

11/8 3주차 잔여 묶음: [인프라 조건부 선정·현재 mTLS 부하/복구](infrastructure-selection-acceptance.md). 채희주가 동시성1/4/8·3반복의576요청(153허용/423거부), gateway장애3회 전달0·새 grant복구, 인증된 관측·37개 인수와 Linux2560개를 검증했다. 과거 후보 비교 지문과 현재 실행 증거를 연결해 C01/C02는 로컬 조건부, C03는 현재 이미지 재검사/앱 영향 독립 대조 전 보류한다. 운영 승인·대안 후보의 현재 부하 새 비교·팀원 독립 재현·3주차 전체 완료와 구분하며 정확한 head/병합 후 CI는 PR을 따른다.

11/6 [CA leaf 통합 인수](ca-runtime-acceptance.md)는 기존 C04 도구/제어기를 지속 실행
관측 경로에 재사용하는 검증이다. 다른 CA 후보의 새 비교 측정이나 운영 최종 채택으로
확대하지 않으며 CA 키 교체/HA의 연결 인수는 별도다.

11/6 3주차 [C01 지속 실행 통합](persistent-monitoring.md): 잠정 선택한 Prometheus/Alertmanager의
기존 asset digest를 재사용해 mTLS 지속 실행·분리 저장소·실제 경보/복구·버전/설정 고정을 검증한다.
기존 후보 비교 결과를 바꾸거나 운영 채택·C01~C03 최종 승인·독립 재현을 완료로 표시하지 않는다.

11/6 3주차 [선정 실행 경로 고정](runtime-release-lock.md): 기존 NGINX digest와 Python/SQLite/
wheel lock을 재사용해 앱·정책·빌드·실행 구조를 고정하고 실제 이미지/설정을 대조한다. 새 제품
추가나 C01~C03 최종 선정은 아니며 관측 통합·조건부 판정·독립 검토는 남긴다.

11/5 3주차 I4 [앱 정비 복구/남은 선정 표](app-state-recovery.md): 기존 SQLite·암호화/서명·
회수/이력 검증을 재사용하고 새 저장 제품을 추가하지 않았다. 로컬 복구 검증 15개는 C01~C03
최종 도구 선정을 대신하지 않는다. 버전/환경 통합 lock·조건부 판정·독립 대조를 11/22 목표로 유지한다.

11/5 C03 [우선 패치 후 재검사](supply-chain-priority-patches.md): 이미 빌드한 새 이미지 tar를
Syft+Grype/Trivy에 공유하고 동결 DB·같은 도구로 재검사한다. 패치 적용·발견 수 변화를 도구 정확도나
최종 선정으로 바꾸지 않는다. 로컬 Deb·HTTP backport 유지보수와 Lambda OS 잔여를 선정 근거에 포함한다.

11/5 C03 [인프라 영향 조건 검토](supply-chain-impact-review.md)로 과거 고정 이미지의 실제 설치/실행
조건과 공식 vendor를 대조했다. 우선 검증17·특정 pip 완화2를 기록하며 억제/선정 근거로 자동 전환하지 않는다.
현재 이미지 재빌드/재검사와 앱 담당의 독립 검토 후 11/22 선정 판단을 갱신한다.

11/5 C03 후속 [발견 차이 재분석](supply-chain-findings-review.md)은 기존 고정 이미지 원본의
무결성·반복·대조군을 검증해 alias/범위/심각도 차이를 인계한다. 200항목의 실제 영향·새 이미지 검사·
최종 채택·독립 재현은 별도이며 후보 도입/의존성 수정 없이 11/15 차이 조사와 11/22 선정에 연결한다.

11/5 C04 후속 [서비스 데몬 복구](service-daemon-recovery.md)는 기존 Docker·PostgreSQL·step-ca와
현재 보안 checkpoint/authority lease를 재사용한다. 같은 ID의 명시적 복구를 선택해 권한/키/DB 재생성을
피하고 접속 재개 후 상태를 보존한다. 실제 격리 데몬 시험은 제품 간 우열이나 자동 선출/물리 HA 검증이 아니다.

11/4 C04 후속 [부모 Docker 데몬 복구](parent-docker-recovery.md)는 기존 Engine ID·공개
anchor·Linux flock·고정 객체를 재사용한다. 격리된 실제 dockerd 재시작으로 증거 기반 명시적 복구를
검증하며 새 quorum/선출 제품의 채택이나 제품 간 우열을 주장하지 않는다. 운영 적용 검토는 별도다.

11/4 C04 후속: [실행기 컨테이너 유실 복구](actor-container-recovery.md)는 기존 Docker의
고정 이름/ID와 생존 볼륨 flock·peer-first 기록을 재사용한다. 명시적 대체와 거부 증거를 비교/기록하며
새 분산 선출 제품을 채택했다거나 제품 간 우열을 검증했다고 해석하지 않는다. 물리 분리는 별도 검증이다.

11/4 후속 C04/I4·I6: [관리 호스트 전환 실행기 재개](executor-transition-recovery.md)는 고정 Docker
actor·기존 Linux flock·공개 파일 journal을 재사용한다. 종료/새 콘솔 재개·부분 사본/owner·완료 후 보안
상태를 검증하며 자동 선출/분산 저장 제품 비교나 물리 HA 채택 완료로 처리하지 않는다.

11/4 후속 C04/I4·I6: [관리 실행 호스트·기록 이중화](executor-host-high-availability.md)는 기존 Docker와
고정 CLI를 재사용해 두 실행기·독립 기록·명시적 봉쇄를 시험한다. 자동 선출/분산 저장소 제품 간 비교 결과는
아니다. 논리 호스트/기록 손실·이전 실행 epoch 거부를 로컬에서 검증하고 물리 분리와 운영자 전환 자체의
중단 복구는 후속 비교 조건으로 남긴다. 기존 기능 동결/제출 일정과 담당 배정은 유지한다.

11/4 후속 C04/I4·I6: [관리 전환 재개](control-transition-recovery.md)는 기존 Docker와 호스트
lease를 재사용하고 공개 파일 journal·부분 복제 검증·생성 사양/ID 대조를 추가한다. 별도 분산 저장소나
quorum 제품을 도입한 것으로 기록하지 않는다. 생존 호스트의 process-death 복구와 물리 호스트/선출
제품 비교는 별도이며, 실제 실행 결과와 남은 차이는 연결 문서에 기록한다.

11/4 후속 C04/I4·I6: [관리 영역 이중화](control-plane-high-availability.md)는 기존 Docker/파일
저장 방식을 재사용해 대기 우선 복제·단일 활성 관리자·정지 확인 후 전환을 시험한다. etcd/Patroni·
분산 파일시스템은 실제 비교/도입하지 않았다. 필요가 검증되면 물리 분리·quorum·전환 crash-resume을
후속 비교하고, 이번 로컬 구현으로 그 제품의 우열이나 운영 채택을 결론 내리지 않는다.

11/4 C04/I4·I6 보완: [CA DB·서비스 호스트 복구](ca-db-host-recovery.md)의 PostgreSQL 물리 동기
복제·명시적 정지 증명·새 저장소 재가입·암호화 백업/보안 checkpoint 대조를 별도 로컬 프로필에서
시험한다. 이 결과로 자동 선출 제품 비교·물리 호스트 HA·앱 SQLite 복원까지 채택/완료 처리하지 않는다.

작성일: 2026년 11월 1일 · 11월 3일 진행 갱신 · 기준: `aitest` v0.17.0

11/3 수행 기록: [C03 로컬 비교](technology-decisions/C03-supply-chain.md)와
[M6/C10 후보·평가 계약 초안](m6-evaluation-contract.md)을 추가했다.
전자는 첫 적용의 조건·실측·남은 차이 조사를, 후자는 실제 호출 전 안전·예산 조건을 구분한다.
전체 후보의 비교 완료나 운영 채택을 뜻하지 않으며 원래 주차별 기한은 유지한다.

같은 날 후속으로 [C01 관측·경보 비교](technology-decisions/C01-observability.md)의
읽기 전용 exporter·공통 경보·별도 조회/입력 권한·내부망 시험을 추가했다.
실측 결과는 해당 기록을 따르며 운영 채택·독립 재현 및 전체 주간 완료와 구분한다.

프로젝트에 필요한 기능마다 **요구 정의 → 후보 조사 → 격리된 시험 적용 → 동일 조건 비교 → 채택·미채택 근거 작성 → 선정 구성 통합 → 독립 재현**을 수행한다. 오픈소스, 직접 구현, 기존 기능 재사용과 상용·관리형 프로그램을 같은 요구에서 검토한다. 기능과 운영 부담을 확인한 뒤 선정하며, 유명도나 설치 성공을 채택 근거로 사용하지 않는다.

대시보드 자체 개발은 사용자가 결정한 범위다. 기존 화면을 확장하고 역할·테넌트별 조회, 판단 근거·회수·집행·감사 연결을 검증한다. Grafana·Perses의 추가 설치 비교는 필수 작업에 넣지 않는다. 수집·보존·경보 도구는 별도로 비교할 수 있다.

추가 후속 [C02 HTTP 집행 비교](technology-decisions/C02-http-pep.md)는 기존 인가 API/worker를
재사용해 두 프록시와 독립 합성 문서 서버를 연결한다. 로컬 안전 시험·선정 근거와 운영 통합/독립 재현을
분리하며, 인프라 실행·측정은 채희주 담당이고 앱 계약 대조·독립 재현은 김택희의 후속 검토다.

## 비교 대상과 적용 범위

11/3 추가 [CA 프로세스 HA](ca-high-availability.md)는 기존 step-ca 2대와 공유 PostgreSQL을 사용한다.
Badger 다중 프로세스 공유는 제외하고 MySQL은 미측정 대안으로 남긴다. 노드별 DB mTLS·단일 토큰 소비·
폐기 공유·클라이언트 전환·전 노드 키 교체 검증을 기록한다. 앱 저장소 전환이나 DB/호스트 HA 완료는 아니다.

11/3 후속 [CA·JWK 자동 교체](authority-key-rotation.md)는 step-ca를 재사용해 root/issuer·전체 등록 JWK의
타이머·겹침 신뢰·전 신원 이행·구 권한 제거를 구성한다. 신뢰된 호스트와 네트워크 없는 소프트웨어 보관함
방식이며 HSM/운영 HA/독립 재현은 남은 운영 조건이다. 아래 이전의 관리 키 보류 기록은 당시 기준선이다.

11/3 후속 [개인키 자동 교체](private-key-rotation.md)는 step-ca의 실제 mTLS rekey와 기존 서버 제한 발급을
재사용해 leaf 키 교체를 적용한다. CA/JWK 서명키 교체·HSM/HA·독립 재현은 남은 운영 조건에 포함한다.
아래 이전 I2/전체 hop의 C04 보류 표기는 당시 기준선이며 현재 상태는 이 후속 기록을 우선한다.

11/3 사용자의 자동 발급·갱신 요청으로 C04의 조건부 시험 필요가 확인됐다. [C04 선정 기록](technology-decisions/C04-certificate-lifecycle.md)과
[실행/권한 범위](certificate-automation.md)에 로컬 step-ca·CSR 제한·타이머·pin 배포·재적용을 연결한다.
운영 CA/키 유출 대응/독립 재현과 기존 기한은 별도로 유지한다.

11/3 후속 [선택 운영 경로 전체 mTLS](all-hops-mtls.md)는 C02 NGINX와 C01 Prometheus/Alertmanager
로컬 기준선을 통합한다. 모든 활성 네트워크 hop·관리 조회를 TLS로 시험하되 과거 대안의 HTTP 비교를
덮어쓰지 않는다. C04 자동 CA·최종 운영 채택·독립 검토는 별도이며 일괄 완료로 표시하지 않는다.

11/3 추가 [I2 mTLS](i2-service-mtls.md): C02 로컬 기준선에 서비스 인증과 수동 인증서 교체/폐기 시험을
연결한다. C04는 제한된 로컬 발급의 기준선을 확보하고 자동화 서비스 설치는 보류한다. 실제 step-ca 비교·
운영 채택 완료로 바꾸지 않으며 자동 갱신/발급 권한/CA 운영 요구가 확인되면 비교한다.

후보명은 예시이며 11/8까지 시험 가능한 판·버전·설정과 계약을 확정한다. 각 필수 영역은 기준선과 대안 2개 이내로 시작한다. 아래 목록을 모두 동시에 설치하거나 모든 기능을 새 프로그램으로 교체하지 않는다.

## 공통 실험 절차

1. **요구와 계약 확정:** 기능 공백, 사용자·보호 자원, 필수 안전 조건, 예상 입력/부하, 성공·실패·중단 기준, 표본/반복 수·관측 구간, 자원·시간·비용 상한을 시험 전에 고정한다. 후보에 유리하도록 평가 후 기준을 바꾸지 않는다.
2. **후보 조사:** 공식 명세·라이선스·판/유료 기능 차이·유지보수·보안 공지·지원 플랫폼·계정 필요·보존/외부 전송·이전/철수 방법을 확인한다. 발표용 벤치마크는 실행 환경의 실측과 분리한다.
3. **격리 시험 적용:** 후보별 Compose 프로필·네트워크·볼륨·샘플 설정을 분리하고 한 후보씩 실행한다. 공개/합성 데이터와 최소 권한을 사용한다. 실제 평가 대상의 이미지/바이너리·출처·서명/지문을 검증하고 호스트 관리자 권한·비밀값 접근을 최소화한다.
4. **공통 시험과 측정:** 고정 입력과 장애 시나리오로 비교한다. 동일한 CPU/메모리 제한·디스크·보존·TLS·인증·허용 정책을 적용하고 차이가 불가피하면 기록한다. 초기 시작·준비·복구 시간과 정상 상태를 구분한다. 각 조건은 3회 이상 반복을 기본으로 하고 표본 수·분산·P50/P95의 관측 구간을 함께 남긴다. 표본이 부족하면 일반화하지 않는다.
5. **선정과 통합:** 안전 조건을 통과한 후보의 운영 복잡도·자원·지연·총비용·유지보수·이식성을 비교한다. 선정한 구성만 제품 경로에 통합하고 기존 기준선과 회귀 시험한다. 잠정 선정 후 바꾸면 이유와 재검증을 기록한다.
6. **근거 작성과 교차 재현:** 작성자가 원자료·설정·절차·한계를 남기고 다른 팀원이 재현한다. 결과가 다르면 해결·보류 상태로 기록한다. 미채택·기존 기능 유지·도입 보류도 근거가 있는 결론으로 남긴다.

설치·프로세스 시작은 연결 확인 단계다. 기능·안전 시험, 비교 원자료, 선정 근거와 상대 재현이 있어야 해당 범위의 비교를 완료 처리한다. 구성 전체의 안전성이 아니라 시험한 범위의 통과를 기록한다.

## 선정 근거 기록 양식

결정 기록은 [비교·선정 대장](technology-decisions/README.md)과 [작성 양식](technology-decisions/decision-template.md)을 사용한다. 결과 문서는 실제 시험 후 추가하며 현재 빈 양식을 결과 보고서로 제출하지 않는다.

기록에는 비교 ID·문제와 요구·후보/판/버전·기존 기준선·공식 자료와 확인일·기능 차이·조건·안전 시험·원자료 위치·지문·실패·비용·자원·채택안·미채택 이유·제약·검증자·적용/복구 절차·재검토 조건을 포함한다. 결론은 `채택`, `조건부 채택`, `기존 유지`, `보류`, `탈락`, `미측정`을 구분한다. 문서만 조사한 후보에는 실행 수치·성능 순위·보안 통과를 부여하지 않는다.

## 비용과 실행 경계

이번 변경은 계획과 문서 작업이며 도구 설치·실험·계정 생성·모델 호출은 수행하지 않았다. 개발과 도구 시험은 로컬 Compose를 기본으로 한다. 비용 허용은 기존 사용자 지시의 실제 모델 API 비교 범위를 따른다. 상용·관리형 프로그램은 공개 문서와 제공된 허용 환경으로 검토하며, 이번 계획이 새 유료 계약·체험 가입·자동 결제·외부 데이터 업로드를 지시하지 않는다. 계정·계약·외부 환경이 필요한 후보는 그 조건과 미측정 이유를 기록한다.

AWS 자원 생성·배포, GitHub 업로드, 실계정 변경과 호스트 센서 설치를 이번 계획 수정에서 수행하지 않는다. 서비스 중단·도구 제거 후 기존 볼륨·정책·키·회수 상태를 보존하고 임시 자원을 정리한다. 전체 일정·안전 경계는 [주간 실행 계획](mentoring-priority-roadmap.md)을 따른다.
