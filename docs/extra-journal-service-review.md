# 사건보다 앞선 journal 실행 관측으로 공유 감사 미탐 개선 — v115

2026-11-16 · 채희주 담당 · 무료 로컬 · 전체 목표 active · 목표 전 push·새 CI·병합 보류

원래 1,681,815행을 유지한 비교에서 공유 감사 **TP 0→2, FN 6→4, FP 3 유지, F1 0%→36.36%**를 확인했다. 정밀도 40%·재현율 33.33%로 목표는 미달이다. 기존 인증·웹 감사의 관측 100%와 VPN F1 80%를 보존했고 전체 새 FP·기존 TP 손실·추론 오류는 0이다. 새로 탐지한 두 행은 **Santos 학습 자료의 같은 서비스 사건 시작/종료**이며 독립 공격 두 건이나 새 독립 평가가 아니다.

## 발견한 실제 근거

추가로 Santos·Shaw·Wheeler의 공유 서버 journal·인증·syslog·프로세스 자료 78개 파일, 총 27,554개 디코딩 기록을 조사했다. 단순 SERVICE_START/STOP의 PID 1은 실제 사람/실행 주체를 알려 주지 않는다. 그러나 Santos에서는 audit 사건보다 journal 수신 시각 기준 **3,991µs 앞선** 서비스 프로세스의 표준 출력 기록을 찾았다. 같은 호스트·부팅에서 root UID와 별도 PID·shell script 명령행, 긴 인코딩 형태의 DNS 이름 처리 오류가 보고돼 있었다.

원래 journal의 서비스 시작 기록과 프로세스 기록은 unit/invocation이 같았다. 이것이 현재 audit 행의 invocation이나 부모/호출 사람까지 증명하는 것은 아니다. audit 자체의 auid/session unset 값은 그대로 유지했다. 명령행도 journal이 보고한 관측이며 별도 원격 증명·실제 명령 성공·현재 권한 검증으로 부르지 않는다.

RussellMitchell·Santos·Fox의 정확한 같은 archive에서 감사 원문과 journal이 나왔는지 다시 검증했다. archive SHA·원래 감사 member SHA·journal binary/decoded SHA를 보존했고, 예측에 사용한 12개 journal의 모든 물리 행을 유지한 채 필요한 journal 필드만 투영했다. 사용하지 않는 필드나 평가 집계가 예측기에 들어가지 않도록 했다. 현재 설정 스냅샷·서비스 파일 내용·나중의 승인 자료를 과거 실행 근거로 쓰지 않았다.

## 연결 규칙과 제약

[연결기](../scripts/f1_lab/journal_service_review.py)는 해당 archive의 정확한 공유 서버 경로·machine/host와 source SHA를 확인한다. journal의 시각은 [systemd 필드 명세](https://github.com/systemd/systemd/blob/main/man/systemd.journal-fields.xml)를 참고해 수신 시각과 원래 시각 중 늦은 값으로 제한했다. 예전 원래 시각이 있어도 늦게 수신된 기록은 과거 판정에 소급하지 않는다. 문자열 시각을 정수 마이크로초로 비교한다.

앞서 나온 원본 audit 행과 journal의 audit type/body·serial·원래 시각을 일치시켜 부팅 관계를 확인한다. 현재 행이나 미래 행을 부팅 근거로 쓰지 않는다. 연결한 과거 서비스 시작의 invocation과 프로세스의 unit/invocation이 같아야 하고, 최근 journal의 부팅도 맞아야 한다. 서비스의 새로운 invocation·부팅 재설정·행/serial 역행·원문 변조·누락/불일치는 연결을 막는다.

실행 프로세스는 PID 1과 구분되는 root UID의 shell script 관측이어야 한다. 해당 stdout에 `dig`가 여러 긴 고엔트로피 label과 비호스트명 문자를 가진 이름을 처리하다 실패한 기록이 있어야 한다. DNS 전송 형식의 이름 길이는 [RFC 1035](https://www.rfc-editor.org/rfc/rfc1035.html)의 255 octet 경계에 따라 label 길이 octet과 마지막 root를 포함해 계산한다. 처음에는 표시 문자열 256자 기준으로 시험해 신호 0이었고, 전송 형식 길이의 올바른 계산으로 정정한 뒤 개발 시험에서 2행을 확인했다. 실패한 시험은 보존했다.

이 신호는 **인코딩된 DNS 이름 처리 시도가 근처에서 관측됐다는 추가 검토 근거**다. 오류이므로 패킷 전송이나 유출 성공을 증명하지 않는다. 높은 entropy·긴 이름은 합법적 진단에서도 나올 수 있어 이 조건을 단독 악성/자동 차단 근거로 삼지 않는다. root shell·서비스·부팅·invocation·앞선 수신 시각과 5초 경계를 함께 적용한다. 생소한 unit 이름·도메인·파일명·절대 날짜를 공격 예외로 학습하지 않았다.

현재 audit 행은 systemd PID 1/root의 성공 SERVICE_START/STOP여야 하며, 이미 존재하는 경보·거부·오류·독립 판정은 변경하지 않는다. 원래 미탐의 `unchanged` 판정에만 추가 검토 경보를 붙인다. 해당 audit 행에 invocation 필드가 없으므로 **동일 서비스의 근접한 과거 관측**을 연결한 것이며 정확한 인과/현재 호출 신원 증명은 아니다. 0.95 점수는 검토 동작 표식이며 보정된 공격 확률이 아니다. 자동 집행·접근 허용은 하지 않는다.

## 검증과 제외한 후보

Linux **820건 통과**, 실패/skip 0·Ruff+RUF100 통과다. 새 journal 관측 시험 36건과 staging 시험 8건은 늦은 수신/미래 원래 시각·5초/1µs 경계·정수 시각·현재/앞선 원문 결속·부팅/호스트/unit/invocation 불일치·새 invocation·실제 PID/root/shell 문법·DNS 형식·sidecar 변조·기존 거부/오류·물리 행 보존·지원하지 않는 부분 패키지의 완료 오보고 방지를 검사한다. `.journal~` 복구 파일도 원래 범위와 지문을 확인해 수용한다. 미래의 중복 audit 행이 앞선 부팅 근거를 지우지 않는 시험도 포함한다. 기능 fixture의 통과율은 F1에 더하지 않는다.

미래 중복 처리 수정 후 v115d 전체 실행에서 기존 실행 신원 fixture 1건이 `service_registry_window`로 실패했다(819 통과·setup 오류 1). 동일 source archive의 v115e 재실행은 820건 통과했다. 시간 조건이나 운영 검사를 완화하지 않았다. 정확한 원인은 미확정이며 시간 의존 회귀의 안정성 확인은 남은 과제로 기록한다. 실패한 실행을 삭제하거나 성공으로 바꾸지 않았다.

실제 투영 journal 13,186행의 파일별·부팅별 수신 기준 시각을 대조해 역행 0건을 확인했다. 이는 이번 자료의 관측 검증이며 운영의 시계 역행/다른 호스트 시각 정확성을 보장하지 않는다.

접속량/간격을 추가한 VPN 후보 하나와 peer 변화율의 세 가지 특징 조합도 R/S/Shaw/Wheeler 학습 자료에서 시험했지만 오탐/미탐 감소가 모두 0이라 채택하지 않았다. Fox/Harrison에 이 후보들을 적합하지 않았고 성능이 좋아진 모델로 보고하지 않는다. journal 연결은 모델 재학습 없이 앞선 실제 근거를 더한 규칙이다.

예측기는 network none·UID10001·read-only root·capability 제거·CPU 2/2GiB로 실행했다. 이미지의 기존 프로젝트 문서/테스트/설치 사본을 차단하고 원문·필수 metadata·동결된 v114 기준선 예측·코드만 제공했다. 새 모델 계수나 평가 정답/집계는 제공하지 않았다. 예측을 봉인하고 컨테이너를 제거한 뒤 정답으로 채점했으며 archive·원문·입력·코드 불변과 기능 시험/예측 코드 일치를 확인했다. 단순 native 수집 기능 성공률로 탐지 지표를 대체하지 않는다.

## 남은 작업

공유 감사는 FN 4·FP 3, VPN은 FP 42·별도 Wheeler 학습 FN 9가 남는다. 다른 시점의 오래된 DNS 오류를 가져와 창을 임의로 늘리거나, 없는 사람·실행 주체·기기/권한을 채워 목표 수치를 맞추지 않는다. 추가 사건 당시 네트워크/실행 관측을 검토할 수 있지만 인과와 단순 동시 관측을 구분해야 한다.

원래 6개 보안 영역의 새 독립 인수는 여전히 미완료이며 전체 목표는 active다. 기존에 관측/학습한 공개 자료의 전후 비교라는 한계를 유지한다. push·새 CI·병합·AWS·유료 API·장기 soak는 실행하지 않았다. 운영 기본 탐지기/팀원 앱은 바꾸지 않았고, 이번에 기존 운영 systemd·mTLS 인수를 재실행한 것으로 보고하지 않는다.
