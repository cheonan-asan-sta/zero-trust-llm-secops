# 조사 후보의 운영 맥락 판정

공개 행동 규칙의 조사 후보를 검토된 정상 작업 기준선, 운영자의 승인 내역, 기존 신뢰된 신호 기록과
연결한다. 등록된 수집기가 관측 내용과 운영 세션의 연결을 서명해야 한다. 공개 데이터의 라벨이나
요청자가 보낸 `approved=true` 같은 값은 운영 근거로 사용하지 않는다.

## 판정 기준

| 확인된 상태 | 판정 |
|---|---|
| 현재 대상에 적용되는 검증된 기기 침해, GuardDuty 경보, 정확한 세션 증명 위반 | 위협 |
| 구체적인 원격 셸 실행 시도 | 위협 시도 |
| 서명과 현재 세션, 기준선과 유효한 승인의 범위 및 사용 한도를 충족하고, 전용 실행 증거의 주체와 목적지가 승인 정책과 일치 | 정상 |
| 기준선 또는 승인 누락, 만료, 취소, 대상 불일치, 수량이나 속도 초과 | 판단 보류 |
| 실행 정책이나 증거 누락, 필수 관측 미확인, 실행 증거 만료 또는 충돌 | 판단 보류 |
| 현재 적용 가능한 승인 정책과 확인된 실행 주체 또는 목적지가 불일치 | 승인 범위 위반으로 위협 판정 |
| 정상 격리, 수동 세션 회수, 상태 미확인 신호만 존재 | 침해로 단정하지 않고 판단 보류 |
| 잘못된 서명, 허용되지 않은 출처나 테넌트 | 접수 또는 판정 요청 거부 |

침해 근거가 있으면 정상 기준선과 승인보다 우선한다. 행동 판정 자체는 토큰을 발급하거나 접근을
복원하거나 세션을 회수하지 않는다. 기존 Inbox와 worker가 검증된 침해 신호를 처리하면 기존 정책에
따라 접근을 회수하고, 새 판정기는 그 committed 기록을 읽는다. 승인으로 회수된 접근을 복원할 수 없다.

기기 침해는 해당 기기에, GuardDuty는 해당 사용자와 자원에 적용한다. 세션 증명 위반은 세션 ID,
버전, 사용자, 기기, 자원, 동작, 입력 해시가 모두 일치해야 한다. 다른 테넌트의 기록은 적용하지 않는다.
과거에 검증되어 기록된 침해 근거는 수집기 키가 나중에 만료됐다는 이유만으로 지우지 않는다.

## 수집과 신뢰 경계

`SignedBehaviorCapture`는 `zt-behavior-1` 도메인으로 Ed25519 서명한다. 검증 대상에는 원본 관측,
테넌트, 출처, 키, 주체와 연결 ID, 세션 버전과 입력 해시가 포함된다. 첫 접수는 발행 후 60초 이내이며
아직 만료되지 않아야 한다. 수집 증명 수명은 최대 120초, 포함된 관측은 발행 전 300초 이내로 제한한다.

기존 `TRUSTED_SIGNAL_SOURCES_PATH` 레지스트리에 전용 공개 키와 `behavior_scopes`를 등록한다.
각 범위는 `source`, `user_id`, `device_id`, `resource_id`, `action`, `principal_hash`를 정확하게
명시한다. 사용자와 기기는 해당 출처의 기존 `user_ids`, `device_ids`에도 들어 있어야 한다.
행동 수집용 키를 세션 증명이나 침해 신고용 출처와 공유할 수 없다. 행동 수집기는 완전한 세션 증명이나
기기 침해 신호를 발행할 권한을 얻지 않는다. 기존 출처에 새 범위가 없으면 직렬화와 증명 해시는 유지된다.

서명할 때는 `app.services.trusted_signals.canonical_behavior_capture`가 반환한 바이트를 사용한다.
개인 키는 수집기 쪽에 보관하며 API나 저장소에 업로드하지 않는다. API는 공개 키로 검증한다.

## 기준선과 승인

관리자가 서로 다른 수집 건 3개 이상, 최대 30개를 정상 자료로 검토하고 기준선을 등록한다.
같은 이벤트 ID나 같은 원본 그룹을 재사용한 자료는 중복 표본으로 거부한다. 현재 판정 대상이 기준선의
학습 자료에 포함돼도 정상 판정에 재사용하지 않는다. 원격 셸 시도나 검증된 침해가 있는 자료는 정상
기준선으로 등록할 수 없다.

기준선은 정확한 관측 종류, API 동작, 대상 자원, 명령, 성공 또는 실패 결과의 조합별 최대 횟수,
수집 건 전체 이벤트 수, 기간, 초당 최대 이벤트 수를 기록한다. 현재 조사 후보를 자동으로 학습해
한도를 늘리지 않는다. 이 프로필은 집계형 작업 범위이며 일반적인 순서 이상 탐지 모델은 아니다.
새 자원이나 명령, 다른 결과가 나오면 범위를 벗어난 것으로 보류한다.

접수 당시 세션이 유효했던 사실은 서버가 기록한다. 따라서 그 수집 증명이나 세션 토큰이 나중에
만료돼도 과거 정상 자료의 검토는 가능하다. 다만 그 이후 관련 침해가 확인되면 신규 정상 기준선 등록은
거부한다. 새 작업의 정상 판정에는 그 작업 자체의 현재 유효한 세션과 수집 증명이 필요하다.

기준선은 최대 7일, 개별 승인은 최대 1일이며 승인 기간은 기준선 기간 안에 있어야 한다.
운영 승인에는 기준선의 정확한 범위를 연결한다. 소급 생성은 허용하지 않으며 두 기록 모두 대상 관측이
발생하기 전에 존재해야 한다. `max_uses` 기본값은 1이며 최대 100으로 명시할 수 있다. 한도는 서로 다른
정상 판정 수집 건 수로 계산한다. 같은 건의 재평가는 추가로 소비하지 않으며 이미 사용한 횟수는
나중에 다른 상태로 판정돼도 되돌리지 않는다. 각 수집 건에도 기준선의 수량과 속도 한도가 적용된다.

현재 정상 판정에는 승인의 `execution_policy`와 별도로 서명한 실행 증거도 필요하다. 정책은 승인된
주체, 작업 식별자, 실행 파일 해시와 목적지 목록을 지정한다. 관측된 주체는 정확히 일치해야 하며
각 목적지는 승인 목록에 포함돼야 한다. 필수 관측이 없으면 보류하고 승인 내용으로 채우지 않는다.
기존 정책 없는 승인은 보존하지만 정상 판정을 자동으로 유지하지 않는다. 계약과 수집 절차는
[실행 주체와 반출 목적지 확인](behavior-execution.md)에 정리했다.

## API

이 경로는 기존 로컬 실행 환경에서 제공한다. 기존 운영 환경의 인증과 역할 검사를 재사용한다.

| 경로 | 역할 | 내용 |
|---|---|---|
| `POST /detections/context/captures` | analyst 이상 | 서명된 관측 접수 |
| `POST /detections/context/execution-evidence` | analyst 이상 | 수집 건 전체에 연결된 전용 실행 증거 접수 |
| `POST /detections/context/baselines` | admin | 검토한 수집 ID로 정상 기준선 등록 |
| `POST /detections/context/approvals` | responder 이상 | 기준선에 연결된 기간과 횟수 승인 |
| `POST /detections/context/baselines/{id}/revoke` | admin | 기준선 취소 |
| `POST /detections/context/approvals/{id}/revoke` | responder 이상 | 승인 취소 |
| `POST /detections/context/evaluate` | analyst 이상 | `{"capture_id":"..."}` 판정 |
| `GET /detections/context/history` | viewer 이상 | 기록 종류, ID, 기록자, 시각 조회 |

기준선 등록 본문의 예시는 다음과 같다. 시각은 실제 검토 시점 이후로 지정한다.

```json
{
  "baseline_id": "nightly-backup-v1",
  "capture_ids": ["reviewed-run-1", "reviewed-run-2", "reviewed-run-3"],
  "valid_from": "2026-11-10T09:00:00+09:00",
  "valid_until": "2026-11-11T09:00:00+09:00",
  "note": "검토한 정기 백업 작업"
}
```

승인에는 `approval_id`, `baseline_id`, `valid_from`, `valid_until`, `note`, 선택적인 `max_uses`를
보낸다. 정상 판정에 사용할 새 승인에는 `execution_policy`도 포함한다. 이 필드가 없는 과거 승인은
읽고 보존할 수 있지만 `EXECUTION_POLICY_REQUIRED`로 보류한다. 취소에는 `{"reason":"작업 계획 변경"}`을
보낸다. 판정은 `verdict`, `reason`, `baseline_id`, `approval_id`, `trusted_evidence`, `base_detection`,
`context_digest`, `execution_status`, `execution_evidence_ids`를 반환한다.
`enforcement_eligible`은 계속 `false`다. 정상 판정이 보호 자원의 별도 접근 정책을 우회하지 않는다.

## 지속 보관과 검증

기본 저장소는 기존 `ZERO_TRUST_DB_PATH` 옆의 `<이름>-behavior-context.sqlite3`다.
예를 들어 `/data/zero-trust.sqlite3`이면 `/data/zero-trust-behavior-context.sqlite3`이며 기존 Docker
데이터 볼륨에 함께 보관된다. `BEHAVIOR_CONTEXT_DB_PATH`로 별도 경로를 지정할 수 있으나 정책 DB와
같은 파일을 사용할 수 없다.

접수, 기준선, 승인, 취소, 판정을 별도 SQLite 해시 체인과 끝점 기록으로 보존한다. 한 트랜잭션 안에서
승인 상태와 사용 횟수를 읽고 판정을 추가한다. 손상이나 삭제는 거부하고, 같은 ID에 다른 내용이 오면
충돌로 처리한다. 최대 10,000개 기록, 128 MiB에서 보관 한도를 초과하면 기록을 지우지 않고 중단한다.
운영 규모 확대 전에는 별도의 보관 정리 정책이 필요하다.

전체 앱 백업은 `app-behavior-context.sqlite3`를 정책 DB 및 선택형 JSONL 기록과 함께 암호화한다.
기준선, 승인, 취소, 수집 기록, 정상 판정에 사용한 승인 횟수를 원래 순서대로 보존한다. 복구 체크포인트와
실행 승인 서명에 이 DB의 스키마, 기록 수, 크기와 해시 끝점을 포함한다. 기존 기록을 바꾸거나 삭제하거나
빈 DB로 바꾸면 재기동을 거부한다. 승인된 기록을 보존한 상태에서 새 기록을 추가한 경우에는 재기동할 수 있다.

격리 복원은 기존 세션을 모두 회수하므로 복원 전 토큰은 만료 전에도 거부된다. 기존 승인이 남아 있어도
새로 검증된 세션이 필요하며, 승인 취소와 사용량은 초기화되지 않는다. 복원 중 저장 또는 승인 게시가
실패하면 해당 사본을 실행할 수 없으며 같은 백업으로 새 격리 사본을 만들어 재시도한다.

이 절차는 모든 기록자를 정지한 로컬 정비용이다. 기준선 DB에 SQLite 보조 파일이 남아 있으면 정상 종료를
확인할 수 없으므로 거부한다. 앱의 정상 SQLite 복구와 종료를 완료한 뒤 다시 시도해야 한다. 보조 파일을
삭제해서 검사를 통과시키면 안 된다. 원본에는 쓰지 않는다. 원래 맥락 DB가 없었던 경우에도 복원 사본에는
검증된 빈 DB를 명시적으로 만들고 실행 승인에 포함한다.

소규모 Docker 실행 환경의 메모리 한도를 지키기 위해 백업에 포함되는 원본 파일 합계를 32 MiB로 제한한다.
이를 넘으면 기록을 줄이지 않고 백업을 거부한다. 살아 있는 맥락 저장소의 128 MiB 한도와는 별도다.
기존 mTLS 복구 실행기는 `BEHAVIOR_CONTEXT_DB_PATH`를 비워 두고 정해진 데이터 디렉터리의 기본 경로를
사용한다. 임의 외부 경로나 원본에 고정한 명시 경로는 복원 시 경로 불일치로 거부될 수 있다.
실행 절차는 [앱 전체 저장 계약](app-storage-recovery.md)과 [mTLS 복구](app-mtls-recovery.md)를 따른다.

```bash
python -m pytest -q tests/test_behavior_context*.py
```

테스트는 새 임시 키, 독립 수집 건, 실제 서명 검증, Inbox, worker, 감사 저널과 보호 자원 API를 사용한다.
승인된 정상 업로드와 삭제 및 조회, 관련 침해의 우선 판정, 위조나 타 대상 신호, 승인 만료와 취소,
자료 재사용, 사용 한도, 재시작과 손상을 확인한다. 이는 통제된 로컬 기능 검증이며 공개 자료의 독립
정밀도나 재현율 목표 달성을 의미하지 않는다.

2026-11-10 최초 판정 기능의 로컬 작업 트리 검증에서 관련 109개 테스트가 통과했다. 당시 전체 회귀 테스트는
3,045개 통과, 2개 제외였으며, 제외된 항목은 패치된 Linux 컨테이너 안에서만 실행하는 기존 검사다.
변경 파일의 Ruff 검사와 `git diff --check`도 통과했다. 상세 실행 기록은
`runtime/m7/behavior-context-validation/verification.json`과 같은 폴더의 `pytest.xml`에 보관한다.

후속 백업과 복구 통합 검증에서는 관련 68개를 포함해 전체 3,101개 테스트가 통과했고 Linux 컨테이너
전용 기존 검사 2개는 제외했다. 기록 보존, 승인 잔여 횟수, 취소 재사용 거부, 만료 전 기존 토큰의 HTTP 403,
새 서명 세션의 HTTP 200, 중간 장애 후 재시도 및 변조된 복원본 기동 거부를 확인했다.
원자료는 `runtime/m7/behavior-context-recovery-validation/verification.json`과 `pytest.xml`에 있다.
이후 기존 Docker 가상 디스크를 정지 상태에서 복사하고 파일시스템을 점검해 입출력 오류로 읽기 전용이
됐던 저장소를 복구했다. 설치된 Buildx와 Compose의 검색 경로 및 기본 Docker 연결도 바로잡았다.
기존 프로젝트 DB의 해시는 복구 전후 동일하며, 후속 컨테이너 검증 중 새 입출력 오류는 없었다.

실제 mTLS Docker 복구 시험 13개와 전체 상태 Docker 복구 시험 25개가 모두 통과했다.
기록 중단과 승인 직전 장애, 같은 백업 재사용, 기준선 및 승인 기록 보존, 재시작 후 기록 유지,
복원 전 토큰의 HTTP 403과 새 승인 토큰의 HTTP 200을 확인했다. 별도 고정 시계 시험에서는
만료되지 않은 기존 토큰 3개가 회수로 거부되며 복원하지 않은 대조군은 허용되는지도 확인했다.
두 실행의 애플리케이션 코드는 동일하다. 전체 상태 실행기만 에뮬레이션 환경의 시작 지연을 고려해
준비 대기를 30초에서 90초로 늘리고 제한된 오류 코드 기록을 추가했다. 접근 검사 조건은 유지했다.

원자료는 `runtime/c02/behavior-context-recovery-check-20261110-r2/verification.json`과
`runtime/week3/behavior-context-full-recovery-20261110-r2/verification.json`에 있다.
복구 조치와 초기 실패 기록은 `runtime/m7/behavior-context-recovery-validation/docker-repair.json`에
연결했다. 테스트가 만든 컨테이너, 볼륨, 네트워크와 임시 이미지는 정리했다.
Docker에 넣은 맥락 기록 4개는 보관 계약 확인용 합성 자료이며, 실제 서명과 승인 의미는 위 API
통합 테스트에서 검증한다. 이번 결과는 로컬 기능 검증이며 공개 로그 탐지 정확도나 GitHub CI 결과가 아니다.

새 세션에서의 기존 규칙 및 운영 맥락 판정 비교는 [비교 평가와 실행 결과](behavior-context-evaluation.md)에
정리했다. 기능 및 복구 시험 통과와 탐지 성능 지표는 별도로 해석한다.

## 기록 보관과 복원

서버는 기준선, 승인, 취소, 수집, 실행 증거, 평가와 고위험 대응 이력을 하나의 논리적 기록으로
보존한다. 활성 행이 10,000개에 도달하면 앞부분을 같은 SQLite 파일의 압축 보관 세그먼트로 옮긴다.
활성 삭제와 보관 삽입은 같은 트랜잭션이다. 원래 순번, 본문, 이전 해시와 현재 해시는 바뀌지 않는다.
승인 사용 한도 계산, 취소 여부와 중복 및 충돌 검사는 활성 영역과 보관 영역을 모두 읽는다.

기본 전체 한도는 100,000건과 논리 본문 합계 128 MiB다. 보관 세그먼트 하나는 압축 전 16 MiB,
전체 보관 직렬화는 256 MiB로 제한한다. 한도 도달 시 성공으로 응답하지 않고 자료를 보존한다.
보관은 삭제나 학습용 요약이 아니며 전체 이력 검증 비용도 남는다. 무제한 운영을 보장하지 않는다.

기존 v1 파일은 검증 후 v2로 트랜잭션 안에서 이관한다. 정지된 기록자의 v1 및 v2 백업을 읽을 수
있으며, 기존 복원 승인 핀은 같은 논리적 접두 이력이 유지될 때 이관과 보관 이후에도 유효하다.
손상된 압축 자료, 빠진 행, 다른 본문이나 바뀐 해시는 복원을 거부한다. 전체 앱 복원에는
기존 소스 및 복원 구현 지문 일치 조건도 계속 적용되므로, 이 호환성이 다른 코드로 만든
봉인 백업의 자동 채택을 허용하지는 않는다. 이전의 승인 사용과 취소
기록을 보관했다고 초기화하지 않는다. 앱 전체 복원 후 기존 토큰의 접근 거부 조건도 유지한다.

```bash
.venv/bin/python -m scripts.context_maintenance status --database EXISTING_CONTEXT_DATABASE
.venv/bin/python -m scripts.context_maintenance compact --database EXISTING_CONTEXT_DATABASE --limit 1000
```

이 명령은 기존 파일만 대상으로 하는 로컬 콘솔 명령이다. 추가 HTTP 관리 경로를 열지 않는다.
전체 앱 백업의 별도 파일 및 합계 용량 제한은 그대로 적용되므로 큰 보관 파일도 무제한으로
백업할 수 있다고 해석하지 않는다.
