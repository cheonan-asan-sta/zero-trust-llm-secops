# 관리 영역 이중화와 명시적 전환

2026-11-04 · 로컬 검증용 관리 프로필 · 운영 배포/물리 호스트 HA 완료와 구분

## 무엇이 달라졌나

[CA DB·서비스 호스트 복구](ca-db-host-recovery.md)는 CA/DB 호스트를 잃어도 살아남은 단일 관리
영역으로 복구했다. 이번에는 그 관리 상태를 **별도 Docker named volume 두 묶음**에 저장하고,
한쪽 관리 발행기를 정지한 뒤 다른 사본으로 이전한다. 루트 키를 다시 만들거나 소비/폐기 기록을
초기화해서 서비스를 재개하지 않는다. 기존 탐지·정책·개선 전 평가 데이터/판정은 변경하지 않는다.

| 대상 | 이번 변경 | 경계 |
|---|---|---|
| CA 설정·온라인 issuer, 암호화 root/JWK 보관함 | 두 관리 cell의 별도 저장소, 쓰기/삭제 시 대기 사본 먼저 저장 | 암호와 bundle은 같은 cell에 있어 HSM 보호가 아님 |
| leaf 상태·갱신 자격·미완료 기록 | 양 사본 동기 반영, 활성 발행기 하나와 읽기 전용 대기 감시기 | 업무 서버의 실제 인증서 파일 볼륨은 기존 공유 경로 |
| 관문 intent/checkpoint·DB reader | 관리 cell에 각각 보존, 관문 재생성 후 새 소유자 사용 | CA 데이터는 기존 PostgreSQL이 권위 저장소 |
| 암호화 백업과 백업 키 | 서로 다른 구성 볼륨으로 양 cell에 보존 | 부모 Docker 관리자가 두 사본 모두 접근 가능 |
| 조정기 계획·진행 상태 | 양 Linux control 볼륨이 원본, Windows JSON은 캐시 | 신뢰된 호스트 실행기/파일 잠금은 공통 의존성 |

cell마다 `ca`, `vault`, `leaf`, `renewal`, `witness`, `backups`, `backup_key`, `reader`, `control`
9개 구성 볼륨을 쓴다. root 보관함·백업 키는 `network=none` 단발 작업만 읽는다. 온라인 leaf·관문에는
그 볼륨이나 Docker socket을 연결하지 않는다. 대기는 상태 읽기 전용이며 발급/게시 명령과 네트워크가 없다.

## 동시에 두 관리자가 쓰지 않게 하는 방법

`SECOPS_CONTROL_MIRROR`가 있는 새 프로필만 변경된 저장 규칙을 사용한다. 기존 단일 관리 프로필은
기존 방식으로 동작한다. 허용된 관리 파일을 바꾸기 전에 두 개의 읽기 전용 역할 기록이 실행 당시
기대값과 정확히 같은지 확인한다. 프로젝트·이미지·관리 epoch·활성 cell·cell별 저장소 세대를 묶는다.
누락/변조/이전 세대면 쓰기·삭제·CA 요청을 거부한다. 역할 파일을 임의로 수정해 재개하지 않는다.

대기 파일의 임시 파일 저장·fsync·교체·디렉터리 fsync를 먼저 마친 뒤 활성 파일에 반영한다.
대기 쓰기 실패 시 활성 파일을 바꾸지 않는다. 대기만 앞선 부분 실패는 전체 트랜잭션 성공으로 취급하지
않으며, 작업 전에 양쪽에 남기는 busy 기록/leaf 게시 journal로 안전한 전환 여부를 판단한다.
파일별 복제이므로 여러 파일의 원자적 분산 커밋이나 consensus 보장이 아니다.

신뢰된 호스트 조정기의 파일 lease 아래에서 authority tick과 호스트 복구 작업을 직렬화한다.
알 수 없는 RW 관리 작업이 살아 있으면 전환을 거부한다. 이 검사는 신뢰된 실행기·승인 이미지·Docker
권한 경계 안에서 유효하며 악의적인 관리자나 우회 Docker 실행자를 막는 분산 lease가 아니다.

## 전환 절차와 중단 시 행동

1. 후보 사본의 역할, 조정기 단계, vault/CA 키·공개 설정, 준비된 서명 계획과 개인키의 일치를 검사한다.
   현재 PostgreSQL primary와 후보 witness의 DB system identifier도 같아야 한다.
2. 허용 단계는 `idle`, `prepared`다. 진행 중인 관리 작업, leaf 게시/미완료 activity, 다른 authority
   단계면 거부한다. 오래된 dump나 불확실한 작업을 임의로 완료 처리하지 않는다.
3. 고정 container ID·이미지·재시작 정책을 검사하고 활성 leaf·대기 감시기·양 관문을 정지/제거한다.
   후보를 다시 검사해 첫 검사 이후 활동도 확인한다. 모든 CA 쓰기 프로세스를 정지하고 DB의 CA 세션 0개를
   확인한다. 이 정지 장벽 이후에만 미해결 관문 intent를 대조하고 새 DB checkpoint를 확정한다.
4. 후보를 읽어 기존 활성 cell의 **새 세대·새 볼륨**을 채운다. 관리 epoch를 올려 역할 기록을 양쪽에
   설치한다. 기존 볼륨은 승격 대상에 재사용하지 않는다. 이미지/경로가 고정된 로컬 오프라인 작업으로
   복사하며 root/JWK bundle을 Windows 파일로 꺼내지 않는다. 기존 CA 설정 동기화에서는 온라인
   issuer 키·암호가 신뢰된 호스트 RAM을 통과하므로, 호스트 전체에서 비밀이 비노출된다는 보장은 아니다.
5. leaf는 pause로 둔 채 CA TLS health를 확인한다. 새 leaf·읽기 전용 대기·관문을 구성하고 양쪽 control에
   새 프로필을 보존한다. 관문을 연 뒤 준비했던 동일 계획을 조정기로 이어간다.
6. 첫 전환 전 기존 cell의 역할/CA 설정 파일을 제거해 후보 이외의 사본에 의존하지 않는지 확인한다.
   이전 9개 볼륨을 실제로 제거한 뒤에도 발급·폐기·일회용 토큰 보존과 백업 인증을 대조한다.
   거부 검사에는 유효기간이 30초 이상 남은 토큰/인증서만 사용해 단순 만료를 성공으로 세지 않는다.

전환 도중 실패하면 서비스가 정지/부분 구성 상태로 남을 수 있다. 자동 롤백/자동 선출/전환 자체의
crash-resume은 구현하지 않았다. old profile로 재시도하거나 busy 기록을 지우지 말고, 컨테이너와 양
사본의 상태를 보존해 조사한다. 이 절차를 무중단 SLA나 임의 장애 시 자동 복구로 표현하지 않는다.

## 로컬 재현

Docker Desktop Linux 엔진과 프로젝트 Python 환경만 사용한다. AWS·유료 LLM·실제 계정·호스트 신뢰
저장소는 사용하지 않는다. 고정 CA/DB/DinD 이미지와 wheel은 기존 lock을 재사용한다.

```powershell
.venv\Scripts\python.exe -m scripts.test_control_plane_ha --directory runtime/c02/c04/control-reproduce
.venv\Scripts\python.exe -m pytest tests/test_control_plane_ha.py -q
.venv\Scripts\python.exe -m ruff check .
```

통합 실행기는 새 CA/DB 서비스 호스트를 준비한 뒤 관리 cell A에서 B, 이후 새 A로 이전한다. 자동 정리가
끝난 프로필은 재사용할 수 없다. 실행 중인 승인 프로필에 한해 다음 수동 명령을 사용할 수 있다.

```powershell
.venv\Scripts\python.exe -m scripts.control_plane_ha status --profile <실행중인-profile.json>
.venv\Scripts\python.exe -m scripts.control_plane_ha promote --profile <실행중인-profile.json> --target b --primary a
```

`--target`은 현재 대기 cell, `--primary`는 현재 실제 쓰기 가능한 CA DB 노드다. Windows 조정기 캐시만
삭제되어도 Linux control 사본에서 진행 상태를 읽는다. 양 control/프로필/호스트 실행기 전체 손실은 지원하지
않는다. 호스트 복구 CLI는 management 프로필을 발견하면 새 backend를 선택한다. 두 종류의 장애를
동시에 주입한 전체 조합 시험의 완료를 뜻하지 않는다.

`runtime`에는 비공개 로그/키 관련 시험 자료가 있으므로 통째로 업로드하지 않는다. 공개 결과는 별도로
추린 JSON만 저장한다. 실행기는 자신의 프로젝트 자원만 정리하며 기존 Docker 작업과 사용자 ZIP을 보존한다.

앱·탐지·정책·기존 process-death 테스트 제한은 변경하지 않았다.
4개 실행 프로젝트의 전용 container·volume·network·image tag를 종료 후 같은 작업자의 별도 Docker 조회로 모두 0개임을
확인했다. 전체 회귀용 이미지 태그도 제거했다. 기존 `pod-forensics-20261025-control-plane`은 실행 상태와
동일 ID를 유지했고, 사용자 `docs.zip`/`docs/week03.zip`은 해시가 같고 Git에 추가하지 않았다.

예비 실행은 최종 합계에서 제외한다. 첫 준비 실행은 소스 수정 뒤 중단/정리했다. 두 번째는 이미
봉쇄/제거한 관문에 의존하던 TLS health 검사로 실패해, 키/상태 볼륨을 연결하지 않는 임시 검사로 고쳤다.
그다음 예비 실행은 18개 검사를 진행했으나 캐시 삭제 후 백업 전 quiesce가 Windows 캐시를 직접 읽어
실패했다. 복제된 control을 읽도록 수정했고, 같은 실행 중 검토에서 찾은 전환 직후 CA/백업 저장소 참조를
먼저 새 cell로 변경했다. 기존 CA 설정 파일 유실 조건과 미만료 증명을 추가한 별도 최종 실행을 사용한다.
이 과정에서 기존 TLS 인증·발급 거부·토큰 만료 조건이나 앱 worker 테스트 제한을 느슨하게 바꾸지 않았다.

## 남은 경계

- 관리 cell은 **같은 부모 Docker 엔진·PC/커널**에서 별도 프로세스와 볼륨으로 나뉜다. CA/DB 서비스 호스트의
  두 DinD 데몬과 다르다. 관리 Docker 데몬/물리 디스크/호스트/지역의 독립 장애를 시험한 것이 아니다.
- 호스트 실행기, OS 파일 lease, Docker 권한, 관리 공개 프로필은 공통 신뢰 경계다. etcd/quorum·네트워크
  분할 자동 선출·악의적 관리자 fencing·전역 antirollback·외부 WORM/HSM은 없다.
- 정상 대기/준비 완료 체크포인트에서 명시적 이전한다. 임의 authority/leaf 게시 중간 단계와 전환 도중
  조정기 종료의 자동 복구는 후속이다. 읽기 전용 대기 감시기는 독립 health/election 서비스가 아니다.
- 업무 앱 SQLite/인가 세션·자체 대시보드·공유 업무 인증서 볼륨의 이중화는 포함하지 않는다. 기존 DB
  복원과 관리 장애를 동시에 결합한 재해 복구, 운영 부하/지연/RPO/RTO 보장과 팀원 독립 재현도 후속이다.
