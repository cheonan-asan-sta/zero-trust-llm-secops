# 일반 평가 상한 이후의 세션 보안 전이

일반 세션 평가의 최대 버전 200은 유지한다. 이 상한에 도달한 세션에서도 worker의 위험 관측, watchdog의 증명 만료·출처 무효화, 운영자의 회수를 기록할 수 있도록 보안 전용 버전을 최대 204까지 허용한다. 기존 세션과 이력을 유지하며 버전을 0으로 초기화하거나 새 세대로 바꾸지 않는다.

## 일반 평가와 보안 전용 버전

| 경로 | 계약 |
| --- | --- |
| 일반·서명 세션 평가 | 새 일반 판단은 최대 버전 200. 199→200의 용량 보류를 유지하며 새 grant를 발급하지 않음. 더 강한 DENY는 유지 |
| 지속 위험 관측 | 현재 출처·키·종류/주체 범위를 검증한 뒤 기존 제한을 강화. 200 이후에도 관련 세션에 반영 가능 |
| 주기 재검증 | 증명 만료 보류와 출처·키 무효화 회수를 기록. 이미 처리한 조건은 반복 기록하지 않음 |
| 수동 회수 | 현재 버전 CAS와 responder 권한·테넌트 경계를 검사. 이미 REVOKED이면 같은 버전·같은 이력을 반환 |
| 버전 201~204 | 새 ALLOW·grant 발급·제한 하향 금지. 보안 전이 검증과 연속 버전 조건을 적용 |
| 유효한 버전 204 | DENY/REVOKED만 가능. 이후 같은 회수·점검은 no-op |

제한의 강도는 `ALLOW < STEP_UP < HOLD < DENY`다. 보안 전용 여유는 강도 상승 세 단계와 기존 HOLD에 만료 사유를 추가하는 제한된 한 차례를 수용한다. 같은 사유의 반복 점검·정상 관측·단순 접근 요청으로 여유 버전을 소비하지 않는다. 정상 관측은 기존 누적 위험 근거를 지우지 않는다.

204는 일반 평가 재개를 위한 추가 여유가 아니다. 유효한 최종 상태는 이미 회수된 상태이므로 그 세션의 반복 점검 때문에 다른 정상 후보의 batch가 실패하지 않는다. 같은 입력 재전송과 worker ACK 복구도 기존 관측 표식을 대조하며 새 정책 효과나 버전을 만들지 않는다.

## 수동 회수와 접근 결과

기존 `POST /zero-trust/sessions/{session_id}/revoke`를 사용한다. 요청의 `expected_version`은 1~204이며 조회한 현재 값과 같아야 한다. `note`와 기존 인증·역할 검증도 유지한다. 다른 테넌트의 세션은 404, 오래된 예상 버전은 409다. 이미 REVOKED인 경우에도 현재 버전 검사를 먼저 통과해야 한다.

```json
{"expected_version":201,"note":"확인된 위험으로 접근 회수"}
```

회수는 새 토큰을 발급하지 않으며 이전의 미사용 grant도 다음 보호 접근에서 거부된다. 세션 조회·이력 API는 201~204를 그대로 반환한다. UI는 해당 버전·상태·근거를 표시하고 PEP는 기존 core의 허용·거부 결과를 사용한다. 숫자가 200을 넘었다는 이유로 별도 접근 허용을 만들지 않는다.

## 저장·오류와 코드 정렬

전이는 현재 이력을 읽는 `BEGIN IMMEDIATE` 트랜잭션 안에서 수행한다. 다중 세션의 변경과 관측 표식은 함께 commit하거나 롤백하며, 재시작·동시 처리·lease 재취득으로 같은 효과를 다시 적용하지 않는다. archive에 보관한 이전 세션 판단도 전체 이력 검증에 포함한다.

모델과 저널 검증은 허용되지 않는 201+ 상태, 강도 하향·새 허용, 비연속 버전과 보안 전이 예산 위반을 거부한다. 저장 손상·알 수 없는 상태·journal의 실제 행·segment·byte 한도나 저장 실패에는 실패 폐쇄와 전체 롤백을 유지한다. 유효한 204 회수 상태를 일반적인 용량 초과 오류로 설명하지 않는다.

201+ 판단을 저장한 DB를 읽는 앱·worker·watchdog·관리 도구와 typed client는 새 모델을 함께 지원해야 한다. 업그레이드 전 동일 DB의 실행자를 정지하고 정책·공개 등록·감사를 포함한 일관된 사본을 보호한다. 구형 코드를 섞거나 코드만 downgrade하지 않는다. 전체 DB를 옛 사본으로 덮어써 회수·소비 기록을 되돌리지 않는다.

이번 변경은 세션 세대 갱신, 200 이후 일반 평가 재개, 승인된 위험 해제·재인증 복구, 자동 정상화나 실제 MFA 수행을 추가하지 않는다. [정책 journal](policy-journal-maintenance.md)·[서버 inbox](server-inbox-maintenance.md)·[수집기 spool](continuous-signal-collector.md)의 유한 보관 한도와 정적 인증서·서명키 수명, C04 미통합 및 앱 DB 백업·복원 한계도 유지한다.

## 검증 범위와 증거 구분

일반 평가 199→200에서 새 grant가 없는지, 200 이후 위험·증명 만료·키 폐기·수동 회수가 기록되는지 확인한다. 같은 조건의 반복·동시 실행·이미 REVOKED 회수는 버전·감사를 늘리지 않아야 한다. 오래된 CAS·타 테넌트·권한 없는 요청, 손상된 overflow 판단, 저장 실패의 전체 롤백과 무관 세션 유지도 검사한다.

경계 버전 200을 직접 심는 합성 fixture는 빠른 경계 시험이다. 일반 평가를 누적하여 199→200에 실제로 도달하는 시험과 구분한다. HTTP API·worker·watchdog·archive·재시작을 거친 상태와 실제 PEP의 다음 자원 전달 거부도 별도 근거로 기록한다. TestClient·직접 함수 호출·실제 HTTP·Docker 검사를 구분하며 이전 프로필의 17·26·30개 결과를 새 보안 전이의 성공 수로 사용하지 않는다. 실제 실행 버전·결과·한계와 팀장 독립 재현은 최종 검증 기록에 남긴다.
